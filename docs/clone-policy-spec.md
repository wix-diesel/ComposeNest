# ComposeNest v1 Clone Policy仕様

作成日: 2026-09-21\
仕様版: 1\
状態: 初版。既存の要件・ドメインモデルを具体化した設計判断\
参照: [企画書](product-proposal.md)、[v1 要件定義書](requirements-v1.md)、[v1 ドメインモデル](domain-model.md)

宣言構文は[v1 Template Schema仕様](template-schema-spec.md)で定義済み。inputsのcloneにはPolicy名を書き、資源生成器と固定PolicyはSchema版からCoreが展開する。

## 1. 目的・適用範囲

本仕様は、既存Instanceの確定設定から、新しい独立したInstanceを作成するための規則を定める。Policyの意味、型と用途による制限、組込み生成器、ポート探索、確認、確定、再試行までを対象とする。

v1のCloneはConfiguration onlyである。元データへの書込み、データコピー、Backup／Restore、保存方式の移行、元環境の停止は行わない。bind mountとnamed volumeのどちらを選んでも、全ての永続化対象に新しい領域を割り当てる。

Policyは**作成前の計画を作る規則**である。一度確定したInstanceの再試行時にPolicyを最初から適用し直してはならない。

本書の表は意味の定義であり、YAMLやJSONの構文表ではない。宣言構文はTemplate Schema仕様で具体化し、Rustの型、CLI実装、SQLiteテーブル、OS別パス解決はアーキテクチャ設計へ委ねる。暗号化、多人数利用、v2のデータ移行等は追加しない。

## 2. 用語と評価入力

| 用語 | 定義 |
| --- | --- |
| 元設定 | 元InstanceのCommittedSpec。Dockerから推測した設定や手編集Composeを使わない |
| 元更新版 | Clone開始時のInstance更新版。確定時に変化を確認する |
| 定義Snapshot | 元が保持するTemplateSnapshot。最新カタログへの自動置換は禁止 |
| 項目キー | Template内の安定した識別子。日本語ラベルや配列の表示順をキーにしない |
| 用途（role） | 通常設定、秘密値、公開ポート、内部識別、保存領域等の意味上の区分 |
| 候補値 | 計画内で計算済みだが、まだ資源として確保していない値 |
| 確認済み計画 | 必須項目と明示選択が完了し、現在の差分を確認して作成要求に使う版 |
| 予約 | AllocationRegistryのHeld／Committed。計画の候補とは区別する |
| ユーザー変更 | Policyの初期結果に対し、許可されたフォーム操作で値を明示的に変更すること |

評価入力は、元Instance ID・更新版・確定設定、定義Snapshot、実行対象と競合範囲、管理ルートの解決情報、資源台帳と外部確認結果、ユーザー入力、計画ID・版とする。秘密値を含む入力全体をログへ出力しない。

アプリ設定の新規保存方式はCloneの初期値に使わない。元Instanceの保存方式を引き継ぎ、ユーザーが変更した場合だけ先の方式を変える。

## 3. 適用の優先順位

| 順位 | 制約・入力 | 規則 |
| --- | --- | --- |
| 1 | Coreの安全条件 | ID・Project・全書込み領域の分離、資源一意性、元非変更、秘密の明示確認。Templateやユーザーが解除できない |
| 2 | Snapshotの互換性・入力定義 | 対応型、必須、選択肢、値域、Version別の有効項目を満たす必要がある |
| 3 | Clone Policy | 初期候補と、ユーザーによる選択が必要な箇所を決める |
| 4 | 許可されたユーザー変更 | 1・2を守る範囲で候補を上書きする。入力の再検証と差分更新を行う |
| 5 | 出力への対応付け | 確定した値をComposeへ投影する。ここで新しい乱数・ポート・秘密を発生させない |

危険なPolicyを無言で安全なPolicyへ置き換えるのではなく、Template検証で拒否する。既知の未指定項目には、後述の明文化した既定Policyを使う。

任意の条件式、スクリプト、ホストコマンド、外部HTTPによる値生成は許可しない。項目間の整合検証と、決定済み値からの定型的な出力生成はPolicyとは分ける。

## 4. 5種類のPolicy

| Policy | 評価結果 | 必須の振る舞い |
| --- | --- | --- |
| `copy` | 元の確定値 | 同じ型・同じ値を引き継ぐ。初期値で置き換えず、値を勝手に整形しない。秘密値は追加の明示確認が必要 |
| `regenerate` | 指定した組込み生成器の新しい候補 | 生成器がその用途に適合すること。最初の生成後は計画内に保持する |
| `nextAvailable` | 条件を満たす次の候補 | v1ではHost Portに限定。探索順・検査・確定時再確認は8節に従う |
| `clear` | 未設定 | 空文字、0、falseには変換しない。必須項目の場合は入力されるまで作成不可 |
| `ask` | 未回答の入力・選択 | 現在値を表示しても、閲覧だけでは回答済みにしない。許可された回答の選択後に検証する |

### 4.1 未設定・空文字・0・false

未設定は値がないことを意味する。空文字、整数0、真偽値falseはそれぞれ独立した値であり、元設定に存在していれば`copy`で保持する。空文字や0が妥当かどうかは項目Validationで判断する。

`copy`元が未設定なら先も未設定とする。先で必須になった項目は入力待ちにし、新規作成用のDefaultを黙って埋めない。無効な元値もDefaultで補正せず、変更可能な項目は入力待ち、それ以外はClone不可とする。

`clear`の後にDefaultを再適用してはならない。新規Instance用DefaultとClone Policyを別の処理として扱う。

### 4.2 `ask`の回答

`ask`は「引継ぎ」「新規生成」「入力」「未設定にする」のうち、その項目の型・用途・必須条件で許可される選択肢を使う。別の`ask`を呼び出す入れ子のPolicyは設けない。

- 通常設定: 有効な元値の引継ぎ、手入力、任意項目の未設定を許可する。
- 秘密値: 明示的引継ぎ、組込み生成、手入力、任意項目の未設定を許可する。
- 表示名: 新しい名前の入力のみ。元名を初期表示しても同名は重複検証で拒否する。
- Version・保存方式: 許可された選択肢から選ぶ。初期選択の表示だけでは明示回答を完了しない。

回答完了は計画版と項目キーに紐付ける。その項目の値・選択肢・元値が変わった場合は回答を再確認する。無関係なログ更新や画面再描画は回答を取り消す理由にしない。

## 5. 型・用途別の適用可否

「条件付き」は後述の制約を満たす場合だけ有効。「固定」はTemplateがその挙動を変更できないことを示す。

| 型／用途 | copy | regenerate | nextAvailable | clear | ask | 未指定時 |
| --- | --- | --- | --- | --- | --- | --- |
| 通常文字列 | 可 | 不可 | 不可 | 可 | 可 | copy |
| 通常整数 | 可 | 不可 | 不可 | 可 | 可 | copy |
| 真偽値 | 可 | 不可 | 不可 | 可 | 可 | copy |
| 選択肢 | 可 | 不可 | 不可 | 可 | 可 | copy |
| 秘密文字列 | 明示確認付き | secret-v1のみ | 不可 | 可 | 可 | regenerate |
| 表示名 | 不可 | 不可 | 不可 | 不可 | 固定 | ask |
| Host Port | 不可 | 不可 | 固定 | 不可 | 不可 | nextAvailable |
| Container Port | 固定 | 不可 | 不可 | 不可 | 不可 | copy |
| Instance ID | 不可 | identity-v1固定 | 不可 | 不可 | 不可 | regenerate |
| Compose Project名 | 不可 | project-v1固定 | 不可 | 不可 | 不可 | regenerate |
| 書込み可能な保存領域 | 不可 | storage-v1固定 | 不可 | 不可 | 不可 | regenerate |
| 保存方式 | 可 | 不可 | 不可 | 不可 | 可 | copy |
| サービスVersion | 可 | 不可 | 不可 | 不可 | 可 | copy |
| Imageの参照 | 定義に基づき維持 | 不可 | 不可 | 不可 | 不可 | Versionから導出 |
| Service Name | 固定 | 不可 | 不可 | 不可 | 不可 | copy |

必須の通常項目へ`clear`を宣言すること自体は可能だが、その結果は入力待ちになる。読み取り専用項目に`clear`や回答方法のない`ask`を付けるなど、完了不可能な定義は拒否する。

ユーザーがHost Portへ直接入力することは許可する。これは`ask`へのPolicy変更ではなく、`nextAvailable`が作った候補への明示上書きである。入力後もCoreの範囲・重複検証を省略しない。

秘密文字列を通常文字列に偽装して制約を回避できないよう、Templateで認証情報として扱う値は機密指定を必須にする。実行時に任意の文字列が機密かどうかを完全に推測できるとはしないため、同梱Templateのレビュー対象に含める。

固定の`container_name`、外部共有の書込みvolume、固定の共有ネットワークはv1 Templateで許可しない。コンテナ名はComposeの自動命名へ委ね、新しいProjectの範囲で実行する。

## 6. 項目別の具体的な方針

| 項目 | v1の動作 |
| --- | --- |
| Template ID・定義版・Snapshot | 元のSnapshotを維持。最新版へ自動変更しない |
| Image／Version | 既定は元と同じ。明示的なVersion選択はSnapshotで対応する範囲のみ |
| Memory Limit・Restart Policy | Snapshotが扱う場合は確定値をcopy。作成後の編集機能を追加しない |
| Database Name・Username | copyを既定とし、Clone確認時に有効な値へ変更可能。同じ値であること自体は資源競合ではない |
| Password | regenerateを既定とし、引継ぎは明示選択。生成済み候補を再描画で変えない |
| Host Port | 元ポートの次から探索する。明示入力は再検証する |
| Instance ID・Project | 新しい識別。元の内部名を編集して作らない |
| 保存方式 | 元をcopy。確認画面で方式を変更できるが、データはコピーしない |
| 全保存slot | 選ばれた方式で先専用に割当て。元のパス・volumeを引き継がない |
| 説明等の任意値 | Templateでcopy／clear／askを指定可能 |
| 生成される接続文字列等 | 先の確定したホスト・ポート・認証値から作る。元の完成済み文字列をそのままコピーしない |

### Versionを明示変更した場合

Cloneに限り、Snapshotが対応する別Versionをユーザーが選択できる。これは空の新環境の作成であり、既存DBのアップグレードや移行ではない。

変更後のVersionに応じた項目・保存slot・ポートslotを再解決する。同じ安定キーで型も同じ項目は現在の候補を保持し、新しいValidationで再検証する。削除される項目は差分に示し、追加される項目はPolicyに従う。元値のない`copy`や必須項目は入力待ちとなる。

同一キーの型変更、Versionに対応する定義不足、未対応Snapshotでは確定しない。イメージ名の自由入力やカタログ更新で不足を補うことは行わない。全slotの再評価と確認が必要で、既存の秘密候補が新条件を満たさなければ無言で再生成せず入力・再生成を求める。

同じイメージタグであることはイメージの内容同一性を保証しない。本仕様では保存済みのImage参照を維持し、digestが確定値として保存されている場合は同じVersionのCloneで保持する。digestの取得時期、CPU別選択、タグからの固定方針はTemplate Schema・実行設計に残し、バイナリ完全同一性を本仕様だけで保証しない。

Versionを明示変更した場合は旧Versionのdigestを新Versionへ引き継がず、新たに選んだImage参照として解決する。生成後の参照を確定設定へ固定し、起動再試行を理由に別Versionへ変えない。

## 7. 組込み生成器

生成器はホストコマンドや汎用式ではなく、Coreが提供する有限の機能とする。以下の名前は意味上の契約名であり、Template作者が任意の生成器を指定する構文ではない。[Template Schema仕様](template-schema-spec.md)の6節に従い、Schema版からCoreが対応する生成器版を展開する。

### 7.1 identity-v1

- 暗号学的乱数から128bitの識別候補を生成し、小文字の32桁16進文字列で表す。
- 管理範囲内の有効・削除済みInstance IDと重複しないことを確認する。
- 計画内で候補を保持し、作成確定時に一意性を再確認する。
- 同じ候補からProject名と保存領域候補を導出する。確定後は二度と再生成しない。

### 7.2 project-v1

- 形式は`cn-<新Instance ID>`とする。表示名・DB名・元Project名を材料にしない。
- RuntimeTarget内の管理台帳とDocker上の既存Projectとの競合を検証する。
- 計画段階で競合した場合は新ID候補を割り当て直し、依存するProject・保存領域候補を再計算する。
- 作成確定後に外部競合や所有不明が判明したら処理を保留する。同じInstanceのID／Projectを変更して回避しない。

### 7.3 storage-v1

- 各書込み可能なStorageSlotIdについて、新Instance IDとslotに紐付く割当て候補を生成する。
- named volumeの実名は`cn-<新Instance ID>-<StorageSlotId>`とする。
- v1のStorageSlotIdとPortSlotIdは、小文字英字で始まり、続きは小文字英数字またはハイフン、全長1〜32文字の安定キーとする。表示ラベルとは別に定義する。
- bind mountは管理ルート内のデータ専用領域へ割り当てる。具体的なディレクトリ階層は保存設計で決め、Instance IDとslotから安定して解決する。
- named volume実体はDocker管理であり、管理ルート配下のホストパスへ変換しない。
- 全slotで元環境・他環境・削除後の保持領域との非共有を検証する。同名・同パスが空でも、新規作成で取り込まない。

既存領域にぶつかった場合、計画段階ならID候補の再割当てと全領域候補の再確認を行う。確定後は所有不明として保留する。作成途中の再試行で同じ実体を使えるかはOperationと所有証拠を照合して判断し、単に名前が同じという理由で採用しない。

### 7.4 secret-v1

- 暗号学的に安全な乱数を使い、`A-Z`、`a-z`、`0-9`、`_`、`-`の64文字から各文字を一様に選び、32文字の秘密値を生成する。
- この生成空間は192bitである。Templateはv1で文字集合や長さを任意変更できない。
- 同一秘密項目の元値と一致した場合は生成し直す。別の計画との全件比較や秘密の一意性台帳は設けない。
- 同じ計画の別の生成対象秘密と偶然一致した場合も生成し直す。
- Templateが32文字やこの文字集合を受け入れない場合は生成器不適合として拒否する。短い値へ無断で切り詰めない。対応するTemplateは`ask`で手入力等を使う。
- 宣言の互換性を確認したうえで、生成候補にも項目Validationを適用する。追加条件で不合格なら生成器不適合とし、条件に合うまで無制限に乱数を引き直す処理はしない。
- 手入力の秘密はTemplateのValidationに従い、32文字に限定しない。空白のtrim、Unicode正規化、文字の置換を自動実行しない。

### 7.5 生成失敗と安定性

識別子衝突や秘密値の偶然一致による再生成は、1回の要求で最大8候補までとする。上限到達または乱数源利用不能なら生成失敗として停止し、時刻・連番・短い乱数へフォールバックしない。

権限不足やDocker接続不能を「衝突」と扱って8回繰り返さない。その場で判定不能として案内する。生成失敗前に有効だった無関係な候補は維持する。

名前と生成器の細部は今回の仕様判断である。v1内で規則を変える必要がある場合は、生成器の版を区別し、確定済みInstanceの識別子・秘密値・保存先を再生成しない。

## 8. `nextAvailable`とポート検証

### 8.1 対象と探索順

1. v1は127.0.0.1／TCP、1024〜65535を対象とする。Templateがさらに制限する場合はその共通範囲を使う。
2. Cloneの自動候補は元のHost Port + 1から昇順に探す。元ポートが65535なら自動候補なしとし、別ポートの入力を求める。
3. 範囲末尾で先頭へ自動的に巻き戻さない。元の確定ポートが未設定のslotでは、Snapshotの推奨Host Portから開始する。推奨値もなければ入力待ちにする。
4. 複数slotでは、ユーザーの明示入力を先に全件検証して計画内の使用予定集合へ追加する。残りをPortSlotIdのASCII昇順で評価する。
5. 自動候補に選んだ値を計画内の使用予定集合へ追加し、後続slotが同じポートを選ばないようにする。
6. 候補のないslotが1つでもあれば計画全体を未完了にする。部分的な予約確定は行わない。

PortSlotIdで順序を固定するのは同じ入力条件で候補が安定するためであり、UIの表示順を指定するものではない。通常の新規作成では推奨ポートを起点にできるが、Cloneでは元の次から探す規則を使う。

### 8.2 候補を利用不可とする条件

- 同じPortCollisionScopeで他Instanceまたは元InstanceのHeld／Committed予約がある。
- 同じ計画内の別slotが既に使用予定としている。
- Dockerが割り当てている、またはホストの他プロセスが占有している。
- OSの予約・権限制約等で利用できないと分かっている。
- 必要な検査ができず、利用可否を確認できない。

元が停止中でも元の予約を除外しない。明示入力した元と同じポートも拒否する。削除後にReleasedになった予約は台帳上の妨げにはしないが、外部占有を別途検査する。

IPv6や全インターフェースでの既存待受がIPv4ポート利用へ影響する場合も利用可否判定に含める。v1へIPv6公開・UDP・LAN公開の選択肢を追加する意味ではない。

検査の結果は「利用不可」「検査範囲で利用可能」「判定不能」と理由・時刻で保持する。スキャン上限や応答期限に達した場合は「空きなし」と断定せず検査未完了にする。具体的なOS検査方式・期限はAdapter設計で定める。

### 8.3 再提案

ユーザー入力同士が重複する場合は、勝手に片方を変更せず該当slotへエラーを示す。明示入力が以前の自動候補とぶつかった場合は明示入力を優先し、影響する自動slotだけを再探索する。

確定前に自動候補が利用不可になった場合は、その候補の次から再探索する。ほかの有効な候補、秘密値、表示名は保持し、変更されたポートを表示して計画全体を再確認する。ユーザーが明示入力したポートは自動変更せず、入力修正または自動提案へ戻す選択を求める。

プレビュー中はOSポートを占有せず、永続予約も作らない。確定時に台帳と外部状態を再検証し、全ポートをまとめて確定する。確認と実際の起動の間の外部占有は防ぎ切れないため、起動後の失敗検出は必須とする。

## 9. 保存領域の検証

| 時点 | bind mount | named volume |
| --- | --- | --- |
| 計画 | 管理下データ領域に解決でき、元・他・保持領域との同一／親子重複がないことを確認 | 新Instanceとslotに対応する名前が台帳・Docker上で未使用であることを確認 |
| 確定 | ルート、パス解決、書込み条件、重複を再確認し全slotを登録 | 実行対象を再確認し、全slotの識別を登録 |
| 実体作成 | 新規作成の結果と所有証拠を記録。既存フォルダーへ無条件に書かない | 新規作成の結果と所有証拠を記録。既存volumeへ無条件に接続しない |
| 再試行 | 同じ割当てと実体の対応を確認して継続 | 同じ割当てと実体の対応を確認して継続 |

パスの正規化、シンボリックリンク、junction、親子関係、所有・権限の確認は保存Adapterが証拠を返す。チェック後の変化もあり得るため、実体作成時にも安全な対象かを確認する。安全を判断できない場合は停止する。

設定ファイルや読取り専用マウントに元の秘密・ポート・パスを埋め込んだまま残さない。先の確定設定から再生成する。書込み可能な永続領域を「単なる文字列設定」に隠してcopyできるTemplateは拒否する。

作成済み領域が消失した場合は新規初期化へ戻さずMissingとする。処理中断で所有不明な領域が見つかった場合はUnverifiedとし、既存データの取り込みや削除で解決しない。

## 10. 秘密情報の引継ぎと表示

### 10.1 引継ぎの明示確認

秘密項目のPolicyが`copy`でも自動確定は認めない。「元の認証情報を引き継ぐ」の明示選択が必要である。`ask`で引継ぎを選んだ場合も同じ条件とする。

ユーザーが手入力した秘密値が元値と同じ場合は、元と同じ値であることを伏字のまま示し、引継ぎ相当の確認を求める。比較は処理内で行い、値や比較用ハッシュをログへ出さない。元値が取得できない・破損している場合は引継ぎを無効にし、再生成または新規入力を求める。

既定の`regenerate`は生成された新しい秘密値を候補とし、作成画面で「新しく生成」と表示する。元と異なる手入力も「入力した値」と表示できる。空の秘密を許可するかはTemplate検証に従い、任意項目のclearで認証方式まで自動変更しない。

### 10.2 画面・保存

- 通常の差分は伏字と「引継ぎ／新しく生成／入力／未設定」で示す。
- 明示操作で表示・コピーできるが、ログ、差分通知、エラー詳細へ実値を含めない。
- 計画は一時的で、永続下書きとして秘密を保存しない。確定後はv1方針に従って平文保存する。
- コピー・生成・手入力のどれでも、Compose生成時に値を別の値へ変換しない。必要なエスケープは表現上の処理であり、秘密値自体の変更ではない。

## 11. ClonePlanの状態・再計算・確認

### 11.1 状態

| 状態 | 意味 | 作成可否 |
| --- | --- | --- |
| Editing | 入力・候補の計算中 | 不可 |
| NeedsInput | 必須値、明示選択、生成失敗等が未解決 | 不可 |
| Reviewable | 入力・候補検証が完了し、差分を確認できる | 現在版の確認後に確定処理へ進める |
| Stale | 元の更新、定義条件・対象不一致等で現在の計画を使えない | 不可。原因解消後に計画を再構築 |
| Committed | 新InstanceとOperationへ変換済み | 新規作成を繰り返さず既存結果を返す |
| Discarded | 確定前に取消し・画面終了等で破棄 | 不可 |

どの状態でも未確定の計画はデータ領域を作らない。外部確認に失敗しても、元Instanceを停止して検査することはない。

### 11.2 再計算の範囲

| 変更の契機 | 再計算するもの | 保持するもの |
| --- | --- | --- |
| 画面再描画・ログ更新 | なし | 全候補・回答 |
| 表示名変更 | 名前の正規化・重複検証・差分 | ID、保存領域、ポート、秘密 |
| 保存方式変更 | 全保存slotの実体候補とValidation | ID、Project、秘密、ポート、通常設定 |
| ポート入力・競合 | 該当slotと衝突する自動slotの候補 | 無関係なポート、ID、保存領域、秘密 |
| 秘密の明示再生成 | 指定した秘密項目 | 他項目 |
| 計画段階のID／Project／領域識別の衝突 | 新IDと全てのID依存候補 | 通常設定、秘密、利用可能なポート |
| Version変更 | 有効項目・slot・Image対応・全Validation | 安定キーと型が一致する有効な入力。詳細は6節 |
| 元の更新版変更・削除 | 計画をStaleにし、元を再選択・再構築 | 古い計画を作成要求には使わない |

計画全体に単調増加する版を持たせる。意味のある候補や入力が変われば版を進め、全体の作成確認を無効にする。項目別回答は、その項目と回答の意味が変わらなければ保持できる。元設定や選択肢が変わった回答は保持しない。

### 11.3 差分の情報

各項目に元値、先候補、Policy、値の由来、変更有無、入力・検証状態、確認の要否を持たせる。値の由来は「引継ぎ」「自動生成」「自動提案」「ユーザー入力」「未設定」「導出値」とする。

例えばユーザーがcopy候補を手入力で同じ値にした場合、差分はなしでも由来はユーザー入力とする。clear元が既に未設定なら差分なしでもPolicyはclearのままとする。由来と値が変わったかを一つの状態へ潰さない。

差分画面では、新しい用途名、Version、公開ポート、保存方式、データ保存領域、DB名等、秘密の扱いを示す。内部ID・Project等は詳細へまとめてもよい。必ず「設定のみ複製。元のDBデータはコピーしません」と表示する。

## 12. 評価・確定の順序

### 12.1 計画の構築

1. 元がManagedで、未解決の変更Operationがないことを確認する。Retiring／Retiredは対象外。
2. 元の更新版・CommittedSpec・Snapshotを一貫した組として読み取る。
3. Snapshot、Policy、用途、生成器の組合せを検証する。
4. Templateの確定値をキーで対応付け、copy／clear／askと通常の生成を評価する。
5. Versionと保存方式の選択を解決し、有効なslotを確定する。
6. 新ID・Project・全保存領域候補を生成する。
7. 明示ポートを検証し、残りのポートを探索する。
8. 通常項目、秘密の扱い、項目間整合、禁止参照を検証する。
9. 差分と未回答・エラーを表示する。有効ならReviewableにする。

実行観測が起動中から停止中に変わっただけでは、元設定は変わらない。元を変更するOperationが実行中なら一時的に受付・確定を止めるが、完了後に元の更新版が変わっていなければ再検証して計画を使える。設定変更や削除を伴う場合はStaleとする。

### 12.2 作成確定

1. 要求された計画IDと現在の計画版、ユーザーの作成確認、全項目の回答を確認する。
2. 元の更新版・Managed状態・未解決Operationの不在と、RuntimeTargetの一致を再検証する。
3. 名前、全ポート、全保存候補、外部状態を再検証する。
4. 候補を変える必要があれば計画を更新して確認へ戻す。まだInstanceを作らない。
5. 新Instance、固定したSpec・Snapshot、全割当て、全Committedポート予約、Operation、計画と作成結果の対応を論理的に同時記録する。
6. 計画をCommittedとし、以後の処理を記録済みOperationとして継続する。
7. 保存領域準備、Compose生成、構成検証、起動、Ready確認へ進む。

5の確定では、元更新版・名前・台帳の重複を最後に再確認し、別処理との競合を防ぐ。外部プロセスの占有までSQLiteの確定で排他できるとは扱わない。

外部処理まで含む単一トランザクションは要求しない。保存後の失敗は、登録されていない環境へ戻すのではなく、同じInstanceに対するOperation失敗として扱う。

### 12.3 二重送信

同じ管理範囲と計画IDは、最大1つの作成結果へ対応する。確定後に同じ作成要求が再送された場合は、既存のInstance ID・Operation IDを返し、2つ目を作らない。

未確定の古い計画版の要求は拒否する。確定済み計画への別版要求も新規作成とみなさず、確定済み結果と不一致を示す。別の複製を作るには新しい計画IDを発行する。

応答が途切れた場合は計画IDから確定結果を照会する。確定できたか不明なまま新計画を自動発行しない。再送対応の記録はOperationとともに永続化し、一時的な画面メモリーだけに依存しない。

## 13. 確定後の失敗と再試行

### 13.1 再試行で保持する値

Instance ID、Project、Snapshot、Image／Version、全保存領域割当て、DB名・Username・Password、その他確定済み設定、Operation IDは保持する。試行番号を増やし、外部状態を再確認して進める。

再試行ではcopy／regenerate／askを再評価しない。元Instanceの設定変更や削除も確定後の先環境に影響させない。再試行ボタンは「もう1つCloneを作る」操作ではない。

### 13.2 起動時のポート競合

1. 失敗理由と自分の実体を照合する。結果不明や前のCLI処理が未終了なら、新しい試行を重ねない。
2. OperationをAwaitingDecisionにし、影響するポートの候補を提示する。
3. ユーザーの確認後に新ポートをHeldとして確保し、旧CommittedとPendingChangeを保持する。
4. 同じ保存領域・秘密で新構成を生成・検証・反映する。
5. 元の作成意図が起動であるため、新構成でReadyを確認して設定・予約を切り替える。通常の停止中EditPortとは成功時の実行状態が異なる。
6. 旧ポートを使う自分の実体がないことを確認して旧予約を解放する。

複数ポートの復旧も集合として確定する。新候補も競合した場合は再度確認へ戻し、勝手な接続先変更を続けない。新Heldが不要になった場合の解放も、それを使う自分の実体がないと照合してから行う。

### 13.3 その他の失敗

| 失敗 | 対応 |
| --- | --- |
| イメージ取得失敗・Docker停止 | 同じ確定情報を保持。前提回復後に再試行 |
| 構成Validation失敗 | 起動しない。原因を示す。別Template版や秘密へ自動置換しない |
| 初期化途中・Ready待ちタイムアウト | MayHaveInitializedとして扱う。再観測し、必要なら同じ値で再試行 |
| 割当て領域の所有不明 | Unverified。既存領域を勝手に取り込まない |
| 以前存在した領域の消失 | Missing。新しい空領域を生成しない |
| 応答断・アプリ異常終了 | OutcomeUnknownとしてOperationと実体を照合。確認前に重複実行しない |
| 秘密・Version・保存方式そのものを変えたい | 同じInstanceの再試行では変更しない。必要なら失敗操作を安全に終了し、新規計画を作る |

DBデータの書込みがなかったと推測して値をリセットしない。再試行のためにデータを削除する処理はない。

## 14. キャンセルと予約の存続

| 時点 | 操作 | 結果 |
| --- | --- | --- |
| 計画中・確定前 | 取消し | 計画を破棄。実体・永続予約は存在しない |
| 確定要求の応答待ち | 画面を閉じる | 確定取消しとみなさない。計画IDで結果を確認する |
| 確定後・実行中 | アプリ終了 | 元環境を操作せず、先Operationは再起動後に照合。データ・予約は維持 |
| 確定後・失敗 | 操作を終了 | 外部結果を照合してAbandonedにできる。InstanceとCommitted予約は残る |
| 先Instanceを削除 | データ保持の削除 | ドメインの削除規則に従い、実行資源除去後に予約解放。データはRetained |

Held／Committedは時間経過だけで解放しない。元Instanceが停止・削除されたことを理由に、先の予約や保存領域を自動変更しない。

## 15. エラー分類

以下はCoreが返す理由識別子の案であり、APIレスポンス形式を固定しない。日本語文言はUIで対応付ける。

| 識別子 | 検出例 | 回復方法 |
| --- | --- | --- |
| POLICY_NOT_ALLOWED | 保存領域にcopy、通常整数にregenerate | Templateを修正。黙って置換しない |
| POLICY_GENERATOR_INCOMPATIBLE | 秘密項目がsecret-v1の文字集合・長さを許可しない | 対応するPolicy／Validationへ修正 |
| SOURCE_SNAPSHOT_INVALID | 定義破損・未知Schema・キー型不整合 | Cloneを中止し原因を案内 |
| SOURCE_CHANGED | 計画開始後に元更新版が変化 | 計画を再構築して確認 |
| SOURCE_NOT_AVAILABLE | Retiring／Retired、未解決変更操作 | 対象変更または元操作解決後に再確認 |
| INPUT_REQUIRED | 必須値が未設定、ask未回答 | 該当項目の入力・選択 |
| SECRET_CONFIRMATION_REQUIRED | 秘密の引継ぎ未確認 | 明示選択または新しい秘密へ変更 |
| GENERATION_FAILED | 乱数源失敗・候補上限到達 | 自動フォールバックせず再試行案内 |
| PORT_CONFLICT | 管理予約・外部占有・計画内重複 | 入力修正または再提案 |
| PORT_SEARCH_EXHAUSTED | 許可範囲を最後まで調べて候補なし | 別の許可ポートを入力 |
| RESOURCE_CHECK_INCOMPLETE | 検査不能・検査期限到達 | 接続・権限等を解消し再確認 |
| STORAGE_CONFLICT | 同一／親子領域、既存volume | 確定前は新候補と再確認、確定後は保留 |
| STORAGE_MISSING_OR_UNVERIFIED | 再試行時の消失・所有不明 | 実体照合。新規初期化しない |
| TARGET_MISMATCH | RuntimeTargetが変化 | 正しい対象を確認するまで停止 |
| PLAN_REVISION_MISMATCH | 古い画面の確定要求 | 現在の計画・差分を表示 |
| PLAN_ALREADY_COMMITTED | 確定済み計画への別版要求 | 既存作成結果を示す。二重作成しない |

エラーに秘密値、秘密入りCompose、元環境の全設定を添付しない。フィールドキー、対象ID、公開ポート等の必要な識別情報だけを返す。

## 16. Template定義への引継ぎ契約

Template Schemaでは少なくとも、安定キー、入力型、用途、必須、Validation、機密指定、Version条件、Clone Policy、必要な生成器、入力・選択の可否を宣言できる必要がある。

Policy未指定時は5節の既定値で意味を確定し、正規化された定義をSnapshotへ保持する。既存Snapshotを新しい既定規則で再解釈しないよう、Policy仕様版と生成器版を識別できるようにする。未知の仕様版は拒否する。

宣言上の自由な値参照や実行順指定はv1に設けない。Version→有効項目、ID→Project／保存領域、設定値→生成物という既知の依存だけを扱う。Templateの表示順でPolicy結果が変わってはならない。

### 宣言内容の例（構文ではない）

| 項目 | 用途・型 | Policy | 許可される確認時の変更 |
| --- | --- | --- | --- |
| Instanceの表示名 | Coreの表示名 | ask固定 | 新しい名前を入力 |
| PostgreSQL Version | 対応Versionの選択 | copy | Snapshot内の対応Versionを明示選択 |
| database | 通常文字列・必須 | copy | 新しいDB名を入力 |
| username | 通常文字列・必須 | copy | 新しいUsernameを入力 |
| password | 秘密文字列・必須 | regenerate、secret-v1 | 再生成、入力、明示的な引継ぎ |
| databaseポートslot | Host Port | nextAvailable固定 | 許可範囲のポート入力 |
| data保存slot | 書込み領域 | regenerate、storage-v1固定 | パス入力は不可。Instance全体の保存方式を選択 |
| Redisの認証値 | 秘密文字列 | regenerate、secret-v1 | Templateで認証を扱う場合に同じ規則を適用 |

RedisにDB名やUsernameを形式的に追加する必要はない。サービスが実際に持つ入力と実行設定だけを定義する。

| CP-T25 | 同一計画の確定要求を二重送信 | Instance・Operationが1つ。既存結果を返す | MGT-10、INV-09 |

| CP-T27 | Cloneの起動失敗後に再試行 | 同一ID・Project・領域・秘密・Operation、試行番号だけ増加 | AC-09、INV-05 |
| CP-T28 | 起動直前のポート競合、復旧承認 | 旧Committed＋新Heldを保持、Ready確認後に切替え | AC-08、INV-16 |
| CP-T29 | 復旧反映直後にアプリ終了 | PendingChangeと実体を照合。旧／新予約を早期解放しない | AC-14、INV-16 |
| CP-T30 | 初期化済み領域が消失 | Missingとして停止。再生成・空DB化しない | AC-11、INV-06 |
| CP-T31 | 確定前取消し／確定後応答断 | 前者は資源なし。後者は計画IDで結果照会、二重作成しない | DM-07、REC-05 |
| CP-T32 | Template版更新・削除 | 元Snapshotを使用。現行既定値で再解釈しない | AC-16、INV-08 |
| CP-T33 | Version変更で必須項目・slot追加 | 全条件を再評価し、元値のない必須copyは入力待ち | TPL-05、CLN-06 |
| CP-T34 | Version変更で秘密Validation不適合 | 候補を無言で切り詰め・再生成せず再入力要求 | SEC-05、INV-05 |
| CP-T35 | 生成接続文字列を元から引き継ごうとする | 先のポート・秘密から生成し直す | CRT-06、INV-02 |
| CP-T36 | 新規保存方式の既定値をnamedへ変更後にbind元をClone | bindを初期値にする | STO-02・03、INV-15 |

CP-T20〜22、27〜30はPostgreSQL／Redisと両保存方式を対象にする。元の業務データを用意し、先に存在しないこと、先への書込みが元へ影響しないことを確認する。実際のポート・パス検査とCLIの動作は各OSで検証する。

## 18. 決定事項と次の成果物

今回、5種類のPolicyの意味、用途別の制約、未設定の扱い、組込み生成器、ポート探索順、秘密の明示確認、再計算範囲、確定の二重送信防止、再試行時の値維持を具体化した。

Template Schemaで正式構文、Version別の宣言方法、固定のタグ／digest参照の扱いを具体化した。後続へ残すのは、Image取得・再試行時の解決、OS検査の方法と期限、所有証拠、永続化・CLI手順、UIのレイアウトである。これらを理由にCoreの安全条件を変更しない。

**Template Schema仕様は作成済み**。本書の用途・型・Policy適用表、安定slotキー、仕様版と生成器版を引き継いだ宣言形式と、PostgreSQL・Redisの定義例を用意した。[アーキテクチャ設計](architecture-v1.md)で検証・保存・外部実行の責務を定め、実機での両保存方式・Clone検証は[v1 実装タスク一覧](https://github.com/wix-diesel/ComposeNest/issues/56)へ整理している。
