### 改訂時に確定した方針

- v1はWindows x86_64の64bit OS、macOS ARM64、LinuxはUbuntu 26.04のx86_64（64bit）のみを対象とする。Ubuntu ARM64はv1対象外とする。
- データ保存はbind mountを既定とし、ユーザー設定でnamed volumeも選択できる。両方式をv1の必須対象とする。
- v1の秘密情報は平文で保存する。暗号化・OS資格情報ストア連携は必須にしない。
- ユーザーがCLIで環境を起動する体験は現時点の検討・受入対象から外す。アプリ内部でのDocker／Compose CLI利用は継続する。
- React／Tauri／Rust／SQLiteを採用する。TypeScript／Viteもフロントエンド構成案として継続する。
- v1のUIは日本語のみ。将来の英語等への拡張に備え、文言と表示ロジックを分離する。
- v2では管理アプリ自体をコンテナで起動し、Webブラウザから利用できるようにする。v1で共通Coreの分離を行い、HTTP提供とコンテナ配布の実装はv2とする。
- Docker／Composeは現時点の最新安定版を利用する。2026-09-21の基準はEngine／CLI 29.8.1、Compose 5.5.1。参照元と更新方針は要件定義書3.2節に記載する。
- 管理ルートはシステム共通データ領域とし、Windowsは`C:\ProgramData\ComposeNest`、Ubuntuは`/var/lib/composenest`、macOSは`/Library/Application Support/ComposeNest`を採用する。権限設定と具体構成は[アーキテクチャ設計](architecture-v1.md)の6節で定め、実機検証を残件とする。

後続成果物: [v1 要件定義書](requirements-v1.md)、[v1 ドメインモデル](domain-model.md)、[v1 Clone Policy仕様](clone-policy-spec.md)、[v1 Template Schema仕様](template-schema-spec.md)。本書のMVPはv1を指す。

## 1. プロダクト概要

ComposeNestは、Docker初心者がテンプレートを選び、用途名と必要最低限の設定を入力するだけで、ローカル開発用のデータベースや関連サービスを作成・管理できるクロスプラットフォームOSSである。

中心となる体験は「PostgreSQLを起動する」と「AppAで使っている構成を、AppB用に安全に複製する」の2つ。ユーザーがComposeの設定項目を理解して手作業で修正する負担を減らす。

v1はWindows・macOS・LinuxにインストールするDesktop-firstのアプリとし、管理アプリを起動するために`docker run`を要求しない。v2では管理アプリのコンテナ配布とブラウザからのアクセスを実現する方向とし、業務ロジックを再利用できる分離をv1から行う。

生成物は通常の`compose.yaml`と必要な補助ファイルとして保存し、独自DBの中だけに閉じ込めない。v1ではアプリ内部からCompose CLIで実行する。ユーザーによる直接のCLI起動、エクスポート手順、外部編集の取り込みは現時点の検討対象としない。

## 2. 背景・解決したい課題

単一のPostgreSQLを試したいだけでも、Docker Image、Composeファイル、ports、volumes、environment、networks、命名、CLIの理解が必要になる。初心者には目的に到達する前の学習負荷が大きい。

また、既存環境の再利用ではComposeファイルのコピー後にポートや保存先などを変更する必要がある。修正漏れは起動失敗だけでなく、別用途の環境が同じデータを参照する事故につながる。停止中の環境のポートは現在の使用状況だけでは把握できず、後から同時起動したときに競合する。

作成後にも「起動中なのか」「アプリから接続できるのか」「削除するとデータも消えるのか」が分かりにくい。ComposeNestは、初回作成から複製、日常操作、失敗からの復旧までを一続きの利用体験として扱う。

## 3. プロダクトの目的

1. Docker内部概念を先に学ばなくても、開発に必要なサービスを利用開始できるようにする。
2. 既存環境の設定を再利用しつつ、ポート・実行資源・永続データを別環境から分離する。
3. 何のサービスが何の用途で動作しているかを、ユーザー自身が把握できるようにする。
4. 宣言的なTemplate追加によって、OSS Contributorが対応サービスを増やせるようにする。
5. 標準のComposeをファイルとして残し、生成された実行構成を確認可能にする。

本番運用の自動化やDockerの全機能を置き換えることは目的としない。初心者が安全にローカル環境を扱える範囲を優先する。

## 4. ターゲットユーザー

| 優先度 | ユーザー | 利用場面・必要な支援 |
| --- | --- | --- |
| 主対象 | Docker初心者のアプリ開発者、学習者 | PostgreSQLやRedisを早く使いたい。適切な初期値、接続情報、失敗原因の案内が必要 |
| 主対象 | 複数の個人・業務プロジェクトを扱う開発者 | AppA用とAppB用の環境を分けたい。設定の再利用とデータの分離が必要 |
| 副対象 | チームの開発支援担当者・講師 | 標準的な構成をTemplateで提供し、環境準備の説明を減らしたい |
| 拡張の担い手 | OSS Contributor | アプリ本体を修正せず、宣言的な定義と検証でサービスを追加したい |

MVPは自分の端末を使う単一ユーザーを対象とする。共有サーバーの管理者、本番DB運用者、クラスタ管理者の要求はMVPの設計基準にしない。

| ユーザーの要求 | 提供する価値 | 観察できる結果 |

| 実行構成を確認したい | ファイルとして残る標準Compose | アプリが生成した構成を確認できる |

## 6. 既存Docker管理ツールやCompose GUIとの違い

以下はカテゴリーごとの重心を整理したものであり、他製品に個別機能が存在しないと主張するものではない。Docker Desktopにもコンテナ操作やログ確認などがあるため、Start／StopのGUI化だけでは十分な差別化にならない。[Docker Desktop公式資料](https://docs.docker.com/desktop/use-desktop/container/)

| 観点 | 一般的なDocker管理UI | Compose GUI Editor | ComposeNestの重心 |
| --- | --- | --- | --- |
| 主な操作対象 | コンテナ・イメージなどの実行資源 | Composeの設定・構文 | Templateから作る用途別Instance |
| 開始方法 | 既存資源の操作・構成指定 | Composeの作成・編集 | サービス選択と最小限の入力 |
| 複製の設計基準 | 製品による | 設定編集・コピーを支援 | 項目別Policy、停止中予約、保存領域分離、差分確認 |
| 初心者への説明 | Docker概念を使う場面がある | Compose構造を扱う場面がある | 用途、接続先、データの扱いを前面に出す |
| 標準形式との関係 | 製品による | Compose自体を管理 | Instanceから標準Composeを生成して保持 |

競争優位の仮説は「初心者が、既存環境を壊さず、別用途の環境を短い操作で用意できること」にある。後続のユーザー調査では、CLIでのコピーや既存GUIと比べた時間、理解度、失敗率を検証する。

## 7. プロダクトコンセプト

概念の流れは以下とする。

**Template → Instance → Generated Compose → Container Runtime**

- Templateは、サービスについての知識と安全な設定方法を表す。
- Instanceは、ユーザーの用途に対応する環境の永続的な管理単位である。
- Generated Composeは、Instanceの実行可能な標準形式への投影である。
- Container Runtimeは実際にサービスを動作させる。MVPではDockerを対象とする。

MVP提案は「1 Instance = 1 Compose Project = 1つの主要サービス」とする。複数ポートや複数の永続化対象は表現可能にするが、PostgreSQLとRedisをまとめたアプリ一式の構成は将来対象とする。

Instanceはコンテナを停止・再作成しても存続する。表示名の変更によって内部ID、Project名、保存先が変わる設計にはしない。

アプリ内ではInstance設定を生成の基準、Dockerから取得した情報を実行状態の基準とする。外部でComposeが編集された場合は自動上書きを止める。これは生成物の保護であり、直接CLI操作や任意の手編集との双方向同期を提供する要件ではない。

## 8. 用語定義

| 用語 | 定義 |
| --- | --- |
| Template | サービスのイメージ、設定項目、初期値、検証、永続化、準備完了判定、Clone時の振る舞いなどを宣言する再利用可能な定義 |
| Instance | Templateから作成する、このアプリが管理する1つの用途別環境。内部ID、表示名、確定した設定、Templateの版、保存先、実行対象などを持つ |
| Clone | 既存Instanceの設定から、新しいIDと独立した実行資源を持つInstanceを作成する操作。MVPでは元の業務データをコピーしない |
| Compose Project | Composeがサービスやネットワークなどをまとめて識別・分離する単位。ユーザーのアプリ名や表示名とは別の内部識別子を使う |
| Generated Compose | Instanceから生成し、ファイルシステムに保存する標準の`compose.yaml`。必要に応じて秘密情報等の補助ファイルを伴う |
| Data Directory | データ永続化用のホスト側ディレクトリ。Docker named volumeを採用する場合は同じ意味のパスが存在するとは限らない |
| Clone Policy | 各項目を引き継ぐか、新しく割り当てるか、ユーザーに確認するかを定める規則 |
| ポート予約 | 停止中を含む管理Instanceが使用予定のポートを、アプリ内で割当て済みとして扱うこと。OSによる占有ではない |
| Ready | コンテナが実行中で、Templateが定める準備完了条件も満たす状態。任意のクライアントから接続できることまで保証するものではない |

Compose Projectはサービス名が同じ環境同士を分離するためにも使える。このため、Clone時にサービス名を必ず変更する必要はない。[Compose Project名の公式説明](https://docs.docker.com/compose/how-tos/project-name/)

## 10. 各ユースケースの基本フロー

### UC1: 初回起動

1. ユーザーがOS向けパッケージをインストールし、通常のアプリとして起動する。
2. Docker CLIの存在、`docker compose`の利用可否、Docker Engineへの接続を個別に確認する。
3. 対応するバージョン、ローカル接続先、Linuxコンテナを実行できるかを確認する。
4. 利用可能ならTemplates／Instances画面へ進み、「最初の環境を作成」を案内する。
5. 未準備なら「Dockerが未インストール」「起動していない」「権限が不足」「対応外」の原因を分け、公式導入案内と再確認操作を表示する。

Dockerの自動インストールや権限設定の自動変更はMVPに含めない。アプリだけをインストールしてもEngineは別途必要であることを説明する。Engine停止時でも保存済みInstanceの閲覧は可能とし、停止と判定せず「状態を確認できません」と表示する。

### UC2: TemplateからInstance作成

1. ユーザーがPostgreSQLなどを選択する。
2. Templateからフォームを表示する。用途名、Version、接続ポート、Database Name、Username、Password、保存方式、データ保存先を必要性に応じて提示し、推奨値を入力済みにする。保存方式はbind mountを既定とし、named volumeを選択できる。
3. ユーザーが設定を確認し、Createを押す。初回はイメージ取得が必要になることを示す。
4. 入力、対応Version、実行対象を検証する。
5. 管理Instanceの予約、Dockerの割当て、ホスト側の利用状況を調べ、ポートを検証する。
6. 保存領域の存在・権限・重複を確認し、内部ID、Project名、ポート、保存領域を割り当てる。
7. Instanceを作成中として記録し、Composeと補助ファイルを生成する。
8. `docker compose config`で構成を検証する。構文検証の成功と、実際に起動できることは区別する。
9. `docker compose up -d`を実行し、イメージ取得・起動・準備完了待ちの進捗を表示する。
10. 実行状態とHealth Checkを確認し、接続先・認証情報の確認／コピー方法を表示する。

入力エラーは該当項目の近くに示す。構成検証失敗では起動しない。ネットワーク障害、イメージ取得失敗、権限不足、ポート競合、準備完了のタイムアウトは原因別に案内し、設定を保持して再試行できるようにする。失敗後にInstanceや生成済みデータを黙って削除しない。

### UC3: Instance Clone

1. 元Instanceで「複製（設定のみ）」を選択する。元が起動中でも利用できる。
2. 新しい用途名を入力する。
3. 元Instanceが使用したTemplateの版と確定済み設定を基に、Clone Policyを適用する。
4. 新しいID、Project名、保存領域を割り当て、ポート候補と秘密情報を生成する。
5. 「引継ぎ」「自動変更」「入力が必要」を項目ごとに示す。データはコピーされず、新規初期化されることを表示する。
6. ユーザーが差分と接続設定を確認してCreateを押す。
7. UC2と同じ検証・確定・生成・起動処理を実行する。プレビュー後の競合も再確認する。
8. 元環境と複製先を別々に一覧表示し、新しい接続情報を提示する。

確定前のキャンセルでは元環境を変更せず、計画を破棄する。この段階では永続予約やデータ領域を作らない。確定後の画面終了は操作取消しとせず、予約と処理記録を保持する。起動失敗時も元環境を停止・再設定しない。Template版が利用できず保存済み定義でも再現できない場合は、別版への自動置換をせず理由を説明して中止する。

### UC4: Instance管理

1. 一覧でサービス種類、用途名、状態、接続ポートを確認する。
2. 対象Instanceの詳細から操作を選択する。
3. 実行対象と外部変更の有無を確認し、操作を実行する。
4. 実際の状態を再取得して結果を表示する。処理中の二重操作を防ぐ。

| 操作 | MVP提案 |
| --- | --- |
| Start | コンテナが残っていれば起動、存在しなければ保存済みComposeから再作成する。Engine停止時は案内する |
| Stop | サービスを停止する。Instance、データ、ポート予約を保持する |
| Restart | 現在の構成で再起動する。設定変更を適用する操作とは区別する |
| Edit | 表示名と接続ポートに限定する。ポート変更は停止中のみとし、Compose再生成とコンテナ再作成が必要なことを示す |
| Delete | 対象環境の実行資源とアプリの有効な管理登録を削除する。永続データ・復旧用ファイルは残し、場所を表示する。ポート予約は完了後に解放する |
| Clone | UC3を起動する |
| Logs | 件数を制限したログを表示し、再読み込み／追従停止ができる。秘密情報の混入に配慮する |

Deleteは対象名と残るものを確認できる画面を設ける。データの完全削除はMVP対象外とし、残したデータを新規作成で自動再利用しない。削除に失敗した場合は対象と予約を保持し、再試行できる状態にする。

Dockerの実態を再取得して画面へ反映する。Composeファイルの手編集を検出した場合は設定更新・再生成を保留し、差分の存在とファイルの場所を示す。直接CLI操作の利用支援や任意の編集内容の取り込みはMVPに含めない。

### UC5: Template追加

1. Contributorが既存Templateと作成ガイドを参照する。
2. 対応Schemaの範囲で、メタ情報、入力項目、イメージとVersion、Composeへの対応、Health Check、Clone Policyを定義する。
3. Schema、未対応機能、危険な権限、初期値、Clone時の分離を検証する。
4. 管理されたローカルTemplateディレクトリへ定義ファイルを追加し、アプリを再読み込みまたは再起動する。
5. アプリが検証済みの定義からフォームを生成し、作成とCloneを実行できる。
6. 公式配布へ含める場合は、実際の起動・接続・永続化・Cloneと対応OSの検証を経てレビューする。

不正なTemplateは個別に無効化し、既存Instanceや他Templateは利用できるようにする。MVPで本体変更なしに追加できるのは、対応済みの宣言機能で表現できるサービスに限る。

## 11. Clone機能の詳細な考え方

### 11.1 安全性の基準

Clone成功とは、単に新しいコンテナが起動することではない。元Instanceを変更せず、独立した永続化領域を持ち、利用可能な接続先が割り当てられ、ユーザーが変更点を把握できることである。

必須条件は次のとおり。

- 元と先の内部IDおよびCompose Projectが異なる。
- 永続化対象をすべて洗い出し、元の書込み可能データ領域を共有しない。
- 停止中を含む他の管理Instanceの予約と競合するポートを確定しない。
- 元環境のポート、秘密情報、ファイル、コンテナを変更しない。
- 起動に失敗しても元環境は利用を継続できる。
- 新しい環境には元の業務データが存在しない。イメージの初期化処理による初期DB等は作成され得る。

### 11.2 Clone Policyの意味

| Policy | 意味 | 例・注意 |
| --- | --- | --- |
| `copy` | 元の確定済み値を引き継ぐ | Version、同一Project内の論理サービス名 |
| `regenerate` | 用途に対応する生成規則で新しい値を作る | 内部ID、Project名、保存先、Password。単に文字列へ連番を足す規則ではない |
| `nextAvailable` | 指定範囲から未割当ての候補を探す | Host Port。候補提示後も確定時に再確認する |
| `clear` | 元の値を消し、未設定にする | 任意の説明など。必須項目なら入力されるまで作成不可 |
| `ask` | ユーザーの明示的な入力または選択を要求する | 秘密情報の引継ぎ選択、用途固有値 |

MVPではこの5種類を有限の組込み規則として扱うことを提案する。任意コードによる生成や条件分岐言語は導入しない。型ごとに許可するPolicyと生成方法をSchemaで限定し、内部IDやデータ領域の分離などの安全条件はTemplateで無効化できないようにする。

### 11.3 項目別の推奨方針

| 項目 | 推奨方針 | 理由 |
| --- | --- | --- |
| 表示名 | `ask` | AppBなど新しい用途を認識できるようにする |
| 内部ID／Compose Project名 | `regenerate` | 表示名とは別の安定した一意識別子が必要 |
| Docker Image／Version | `copy` | Cloneを意図しない更新にしない |
| Memory Limit／Restart Policy | `copy` | Templateが扱う場合は引き継ぐ。編集UIの高度化はMVP外 |
| Host Port | `nextAvailable` | 起動中・停止中の他環境との競合を避ける |
| Container Port | `copy` | 同じサービスの内部待受ポートを維持する |
| Container Name | 原則、明示設定しない | 一意なProject名とComposeの自動命名を利用する |
| Service Name | 原則`copy` | Project内の論理名であり、別Projectとの同名は許容できる |
| Network | Projectごとの既定ネットワークを新規作成 | MVPでは環境間の意図しない共有を避ける |
| Volume Path／volume識別子 | `regenerate`を必須にする | 元データの共有を防ぐ。未変更の書込み先を残さない |
| 保存方式 | 原則`copy`、Clone確認時に変更可能 | bind mount／named volumeの方式は引き継ぐが、実体は必ず新規割当てする。変更しても元データは移行しない |
| Password | 既定`regenerate`、明示的選択時のみ引継ぎ | 新環境の認証情報を独立させる。再生成を明確に表示する |
| Database Name／Username | 原則`copy`、確認画面で編集可能 | 独立したDBサービス内なら同名であること自体は競合しない |

「Service Nameを常に変更する」「Container Nameを常に指定する」という構想は修正する。Projectによる分離を基本とし、Composeの名前空間を利用する方が変更箇所を減らせる。MVP Templateでは固定の`container_name`や外部共有volumeを許可しない。[Composeサービス仕様](https://docs.docker.com/reference/compose-file/services/)

### 11.4 ポート割当て

例として、AppA PostgreSQLが5432を使用または予約している場合、5433以降から候補を探す。ただし5433が空いているとは限らず、例示値を固定の規則にしない。

候補選定では、管理中Instanceの予約、作成処理中の予約、Dockerのポート割当て、ホスト上のDocker以外のプロセスによる占有を考慮する。予約キーには実行対象、待受アドレス、プロトコル、ポートの意味を含め、少なくともMVPのlocalhost／TCPに対して整合した扱いを定める。

アプリ内の同時作成は割当て確定を排他的に扱う。停止後とアプリ再起動後も予約を維持する。失敗Instanceの予約は再試行用に保持し、キャンセル・削除時の解放と、異常終了後の作成中予約の整理を定義する。

外部プロセスが確認直後にポートを取得する競合は完全には防げない。起動時エラーを検出して代替ポートを提案し、ユーザーの確認後に再生成・再試行する。接続先を確定後に黙って変更しない。OS側の制約で確認できない場合は「空き」と断定しない。

### 11.5 保存領域とデータ

構想にある`/data/app-a/postgres`は説明用の例であり、全OS共通の固定パスにしない。MVP提案ではアプリ管理ルート配下に内部IDベースの新規ディレクトリを作り、ユーザーには保存場所を表示する。任意の既存データディレクトリの指定はMVPから外す。

bind mountを既定とし、パスの正規化、大文字小文字、シンボリックリンクやWindows junction、親子ディレクトリの重複、書込み権限を考慮する。空ではない保存先は自動再利用しない。ユーザーがnamed volumeを選択した場合も、新しい識別子と非共有を検証する。

named volume選択時は、ホスト側の実体パス入力を要求せず「Docker管理のデータ保存領域」と識別名を表示する。bind mountで問題が生じても保存方式を黙って切り替えず、原因の案内とnamed volumeで新規作成する選択肢を示す。両方式の作成・永続化・Clone・削除時の保持をMVP必須とする。

要件案では、アプリ設定に新規作成用の既定方式を持ち、作成画面でも方式を選べるようにする。既定値の変更は既存Instanceへ影響させない。作成済みInstanceの保存方式変更はデータ移行を伴うためMVP外とし、設定Clone先での方式変更だけを許可する。

データCloneは将来機能とする。PostgreSQLの`pg_dump`／`pg_restore`、MySQLのダンプ方式、Redis固有方式などをサービスごとに評価し、整合性、Version互換性、停止要否、失敗時の処理を定義する。稼働中のDBデータディレクトリの単純コピーは採用しない。

### 11.6 確認画面の例

| 項目 | 元: AppA PostgreSQL | 複製先: AppB PostgreSQL | 表示 |
| --- | --- | --- | --- |
| Image | postgres:18 | postgres:18 | 引継ぎ。Versionは例示 |
| 接続ポート | 5432 | 5433（利用可能な場合） | 自動変更 |
| データ保存領域 | AppA専用領域 | 新しいAppB専用領域 | 新規作成 |
| Database Name | app | app | 引継ぎ |
| Password | 非表示 | 非表示 | 新しく生成 |
| DBデータ | 元のデータあり | 元データなし | 設定のみ複製 |

秘密情報の差分は値そのものではなく処理内容を表示する。Project名などの内部値は詳細表示にまとめる。

## 12. Template拡張モデル

TemplateはYAML等の宣言ファイルとし、サービス固有のフォームをアプリ本体へハードコードしない。

後続のTemplate Schema仕様では、Schema 1を共通マニフェスト＋Version別完全定義のパッケージとして具体化した。未実装の単一ファイル案は置き換え、互換形式を設けない。将来はユーザー作成Templateをディレクトリ選択からインポートして利用できるようにする。v1のローカル定義追加にも同じ構文・検証・出所区分・不変版管理を適用し、登録しただけでImage取得やコンテナ起動は行わない。インポート画面、オンラインカタログ、Version定義以外の実行用ファイル同梱等は別の拡張として扱う。

| 定義領域 | 想定内容 |
| --- | --- |
| 識別・互換性 | Template ID、Template版、Schema版、説明、対応OS／CPU、検証済みVersion |
| 実行構成 | Docker image、環境変数、ポート、永続化、Health Check、Restart Policy |
| 入力と表示 | ラベル、説明、型、必須、初期値、選択肢、機密指定、基本／詳細の区分 |
| Validation | 範囲、形式、選択可能値、項目間の限定的な整合条件 |
| Clone | 各項目のPolicy、生成器の種類、確認の必要性 |
| 出力対応 | 入力値を許可済みのCompose項目へ安全に反映する規則 |

MVPのフォームは文字列、整数、真偽値、選択肢、秘密文字列、管理された保存領域表示などに絞る。任意JavaScript、ホスト側スクリプト、自由なCompose断片の挿入、外部プラグイン実行は許可しない。Health Check等のコンテナ内コマンドも信頼境界に含める。

TemplateのVersion一覧は検証済みの集合として配布し、初期値に`latest`を使わない。Instanceには利用したTemplate版と再生成に必要な定義のスナップショットを保持する方針とし、Template更新が既存Instanceの構成を勝手に変更しないようにする。タグが同じでもイメージ内容は変わり得るため、初回解決時にdigestとplatformを保存し、再試行・再作成で再利用する。[アーキテクチャ設計](architecture-v1.md)の8.4節で具体化している。

サービスのVersion差は単なるタグ差とは限らない。PostgreSQL公式イメージでは18以降にデータ配置・推奨マウント位置の変更があるため、対応Versionごとの永続化設定を表現できる必要がある。[PostgreSQL公式イメージ](https://hub.docker.com/_/postgres)

公式同梱TemplateはPostgreSQLとRedisをMVP必須とする。MySQL、MongoDB、MinIO、Azurite、RabbitMQは拡張候補とし、現行Schemaで表現できないサービスのためにMVPを拡大しない。

## 13. MVPスコープ

| 領域 | 必須の到達点 |
| --- | --- |
| 配布・前提診断 | Windows／macOS／Linuxの通常のデスクトップアプリ。CLI、Compose、Engine、対象接続先を診断 |
| Template | PostgreSQL・Redisの同梱、Schema検証、ローカル定義追加によるフォーム生成 |
| 作成 | 入力検証、資源割当て、Instance保存、標準Compose生成、構成検証、起動、準備完了判定 |
| Clone | 設定のみ複製、Projectと保存領域の分離、停止中ポート予約、差分確認、競合時の再提案 |
| 管理 | 一覧・詳細、Start／Stop／Restart、限定Edit、データを残すDelete、Logs |
| 接続支援 | 接続ホスト、ポート、DB名、認証情報を確認・必要に応じてコピー |
| 状態・復旧 | 進捗、失敗理由、再試行、外部操作後の再取得、アプリ再起動後の整合確認 |
| 保存方式 | bind mountを既定とし、設定でnamed volumeを選択。両方式でデータ分離と永続化を保証 |
| 標準形式 | Composeと補助ファイルをファイルシステムへ保存し、アプリ内部のCompose CLIで検証・実行 |
| 言語・採用技術 | 日本語UI、React／Tauri／Rust／SQLite。将来の多言語化とv2のCore再利用に備える |
| 安全性 | localhost公開、秘密情報のマスキング、管理外資源を変更しない、データの無断共有・削除を防ぐ |

MVPの実行範囲は、ローカルのDocker Engineで動くLinuxコンテナ、単一ユーザー、管理対象の接続先1つ、単一主要サービスのInstanceとする。Windowsホスト対応とWindowsコンテナ対応を混同しない。

bind mountとnamed volumeを両方提供する。前者はVolume Path、後者はvolume識別子の競合防止を受入条件とする。任意ホストパス入力を後回しにしても、安全な保存領域の自動割当ては削らない。

## 14. MVPでは対応しないこと

- DBデータClone、Backup、Restore、スナップショット、データ移行。

- ユーザーによる直接CLI起動の利用支援・動作保証。内部CLI連携はMVP対象。
- 秘密情報の暗号化・OS資格情報ストア連携、英語等の翻訳、既存データの保存方式移行。
- 既存コンテナの自動取り込み、イメージ・volume・ネットワークの全体管理や一括削除。
- 任意の既存データ保存先の再利用、GUIからのデータ完全削除。
- Dockerの自動インストール、権限昇格の自動化、リモートDocker、複数Context管理。
- Windowsコンテナ、Podman、Kubernetes、Swarm、Docker Engine API Adapterの実装。
- Server／Web版、複数ユーザー、認可、チーム同期、Templateマーケットプレイス。
- 本番向けHA、監視基盤、SLA、DB管理UI、SQL編集。

## 15. 将来的な拡張候補

**v2の方向性として確定しているもの:** 管理アプリをコンテナとして起動し、Reactの画面へWebブラウザからアクセスする提供方式。v1のRust Coreを共有する。管理アプリの状態・Template・生成物の永続化、Dockerへの接続、管理コンテナ内とDockerホスト側のパス対応、認証・公開範囲をv2の設計前に決める。

ブラウザを開く端末、管理アプリのコンテナ、サービスを動かすDockerホストは別の場所であり得る。管理アプリをコンテナ化するだけではホストのbind mountやポート占有確認は同じ意味にならない。Docker socketの利用等によるホスト制御権限も評価する。v2の秘密情報保存方式と複数ユーザー対応は未決で、v1の平文方針を自動適用しない。

以下はv2にすべて含める約束ではない追加候補とする。

| 優先候補 | 内容 | 着手の前提 |
| --- | --- | --- |
| 1 | MySQL、MongoDB、MinIO、Azurite、RabbitMQ等のTemplate | Schemaの表現力と対応イメージの検証 |
| 2 | 複数サービス構成と環境全体Clone | Instance境界、依存関係、内部接続先の再割当て仕様 |
| 3 | サービス固有のBackup／RestoreとデータClone | 整合性と互換性、失敗時復旧の検証 |
| 4 | Template共有・カタログ・更新管理 | 配布元の信頼、署名、互換性方針 |
| 5 | v2 Web版のリモート環境・チーム利用への拡張 | 認証・認可、秘密管理、実行ホストと保存先の再設計 |
| 6 | Docker API／Podman Adapter | 実際の利用需要と実行意味の互換性検証 |

候補は実装の約束ではなく、MVPの利用結果から優先度を見直す。単独サービスでの作成・Cloneが安定するまで範囲を広げない。

## 16. UX上の原則

- 主なナビゲーションはTemplatesとInstancesの2つとする。初回の空画面には作成への導線を置く。
- v1の表示は「テンプレート」「環境」などの日本語とする。英語等の追加に備え、UI文言、エラー文言、Templateの表示文言を識別子や業務ルールから分離する。
- 一覧は「PostgreSQL／AppA DB／利用可能」「Redis／AppA Cache／停止中」のように、サービスと用途を並べる。
- 必須入力を少なくし、ポート・保存先・Passwordは安全な候補を提示する。自動設定した値も後から確認できる。
- portsやvolumesの知識を必須にせず、「接続ポート」「データ保存先」など目的に沿った言葉を使う。
- 「複製」には常に設定のみであることを示し、作成前に引継ぎと変更を確認できるようにする。
- 「実行中」と「利用準備ができた」を区別する。取得不能を停止扱いにしない。
- 長い処理には進捗と次の行動を示す。タイムアウトを即座にデータ破損と表現しない。
- エラーは原因、影響、対処を短く示し、必要な人向けに詳細ログを用意する。
- 削除、再作成、接続先変更の影響を事前に表示する。通常のStart／Stopには不要な確認を増やさない。
- 色だけで状態を伝えず、テキスト、キーボード操作、フォーカス、入力ラベルを整える。
- Compose閲覧とフォルダーを開く操作を詳細画面に提供する。内部IDを通常操作で入力させない。

## 17. クロスプラットフォーム上の制約

| 制約 | 方針・検証事項 |
| --- | --- |
| Windows／macOSの実行基盤 | Linuxコンテナの実行にはVM等の基盤が関わる。Docker Desktop等の準備状態を診断し、アプリの導入と区別する |
| Windowsのパス | ドライブ文字、空白、日本語、区切り、長さ、junctionを検証する。UIでUnix形式の手入力を要求しない |
| Linuxの権限 | Docker接続権限、UID/GID、データディレクトリの書込み、SELinux等を検証する。アプリ全体を管理者実行させることを標準にしない |
| bind mount | マウント元はDocker daemon側のパスであり、リモート接続ではローカルパスと一致しない。このためMVPはローカルに限定する |
| CPU差 | Windowsはx86_64の64bit OSのみ、macOSはARM64のみ、Ubuntu 26.04はx86_64（64bit）のみ。Windows ARM・32bit・macOS Intel・Ubuntu ARM64は対象外。アプリとイメージ双方の対応を検証する |
| ポート制約 | OSの予約範囲、権限、IPv4／IPv6、セキュリティソフトにより起動が失敗し得る。事前確認と起動結果の両方を見る |
| CLI差 | Docker／Composeは現時点の最新安定版を利用し、検証した版を記録する。構造化出力・終了コードを扱い、ローカライズされた文章への依存を避ける |
| GUIからのCLI発見 | ターミナルとGUIでPATHが異なる場合がある。CLI検出と実行先の案内を用意する |
| 配布 | インストーラー、署名、macOS notarization、Linux配布形式を検討する。WebView等の前提も検証する |

Docker Desktopのbind mountはホストとLinux VM間の共有機構を利用する。ホスト依存のパスを含むComposeが、別OSへそのまま移せるとは約束しない。標準形式の生成と、環境全体の移植性は区別する。[bind mount公式仕様](https://docs.docker.com/engine/storage/bind-mounts/)

LinuxはUbuntu 26.04のx86_64（64bit）のみ対応する。macOS最低版はIssue #6で15とし、Windows最低版とDocker提供形態の組合せはリリース前の検証マトリクスで定める。「全Linux環境」を無条件に保証しない。

## 18. セキュリティ上考慮すべき事項

### ネットワークと認証情報

公開ポートは既定で`127.0.0.1`へ限定し、LAN公開はMVP外とする。ホストIPを指定しないポート公開は外部インターフェースへ公開され得るため、安全な既定値を生成側で統一する。[Dockerポート公開の説明](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/)

Passwordは十分な乱数で生成し、フォーム・一覧・ログでは隠す。明示操作での表示／コピーを提供する。コマンド引数、診断情報、クラッシュレポートに秘密情報を出さない。Compose検証出力やコンテナログにも機密情報が含まれ得るため、検証時の出力抑制と表示時の保護を仕様化する。

v1の秘密情報は平文保存とする。アプリ設定と初回の認証情報入力箇所で「このバージョンでは端末内に暗号化せず保存する」ことを説明する。平文保存と画面での常時表示は区別し、通常の表示はマスキングする。

平文の保存先はSQLite、生成Composeまたは補助ファイルとなり得る。正本と生成物の配置はアーキテクチャ設計で定め、不要な複製を避ける。管理ディレクトリは指定したOSのシステム共通領域とし、初期導入時に利用者の書込み権限を設定する。共通パスの採用は複数ユーザー共同管理の追加を意味しない。他ユーザーへ平文秘密を不用意に公開せず、GUIの常時管理者実行を前提にしない。生成物の共有やバージョン管理への登録による漏えいを避ける案内を用意する。暗号化やOS資格情報ストア連携をv1の受入条件にはしない。

### Templateと実行権限

Templateは単なる見た目の設定ではなく、コンテナを実行する入力である。公式レビュー済み定義を既定とし、追加する定義の出所を示す。スキーマ検証だけでイメージ自体の安全性を保証しない。

MVPの管理対象Templateでは特権コンテナ、Docker socketのマウント、ホスト全体のマウント、host network、任意ホストコマンドなどを許可しない。v2の管理アプリ自体へのDocker接続権限とは別の制約として扱う。入力値をシェル文字列へ連結せず、CLIは固定された操作と引数配列で実行する。Composeの変数展開でPassword中の文字が変化しないことも検証する。

Docker操作はホストに強い影響を与え得るため、UIから任意CLIを実行できる構造にしない。対象の内部ID、Project、管理ラベル、保存先を確認してから変更し、管理外資源や共有データを削除しない。

OSS公開に向けて、コードのライセンス、依存物・同梱物の配布条件、脆弱性報告窓口、Templateレビュー手順を決める。利用者の構成・認証情報を送信するテレメトリはMVPの前提にしない。

## 19. 技術上の主要リスク

| リスク・構想への指摘 | 影響 | 対応方針・代替案 |
| --- | --- | --- |
| ポートの空き確認を絶対保証と扱う | 確認後の外部占有で起動失敗 | アプリ予約と実占有を区別し、確定時の再確認と起動失敗後の再提案を用意 |
| 生のパス文字列だけで保存先を比較 | 別表記の同じ領域を共有する事故 | 管理ルートと内部IDによる割当て、実体の正規化。named volumeもユーザーの選択肢として提供 |
| 設定値を書き換えれば既存DBも変わると考える | PasswordやDB名の表示と実DBが不一致 | MVP Editを限定。DB内部変更は別機能にする |
| 起動終了コードだけで利用可能と判定 | DB初期化中に接続失敗 | TemplateのHealth Checkと準備完了待ちを設ける |
| SQLite・ファイル・Dockerを単一処理として扱う | 中断で登録と実体が食い違う | 処理段階を記録し、再起動時に照合。再試行の重複を防ぐ。自動データ削除で辻褄を合わせない |
| 外部CLIやCompose編集を無視する | 誤表示や手編集の上書き | 実行状態の再取得、ファイル変更検出、上書き保留 |
| Template更新で既存環境も更新される | Cloneや再生成で構成が変わる | Template版・定義・確定値を保持し、更新は明示操作に分離 |
| イメージのタグと永続化構造の変化 | データ消失に見える状態や起動不能 | 検証済みVersionを限定、Version別定義、digest方針、更新機能の延期 |
| Docker Contextが外部で切り替わる | 別Engineを操作する事故 | Instanceの対象を固定して照合。想定外の接続先では操作を止める |
| 汎用Template言語を作り込みすぎる | MVP遅延、攻撃面拡大 | PostgreSQLとRedisに必要な宣言機能から開始し、任意コードを禁止 |
| CLIの出力形式・挙動差 | 状態判定やエラー処理が壊れる | 最新安定版を基準に検証版を記録し、構造化出力、互換性テストをAdapter境界で管理 |
| Desktop-firstがOS別配布で停滞する | 3OS対応が実質未達 | 早期に各OSでインストール・CLI実行・永続化の最小検証を行う |

PostgreSQL公式イメージの初期化用環境変数は、既存データがある場合のDB設定変更手段ではない。PasswordやDatabase Nameをフォームで変更するだけでは既存DBへ反映できない点を、Edit範囲の制限理由とする。[PostgreSQL公式イメージの初期化条件](https://hub.docker.com/_/postgres)

Composeはコンテナの実行とサービスの準備完了を別に扱う。Health Checkを準備完了の判断に使うが、アプリからの認証成功まで保証するには別の接続検証が必要である。[Composeの起動順序・準備完了の説明](https://docs.docker.com/compose/how-tos/startup-order/)

### 採用技術と設計上の境界

React／Tauri／Rust／SQLiteの採用は確定する。TypeScript／Viteは既存構成案を継続し、Docker CLI／Compose CLIを内部Adapter経由で利用する。後続アーキテクチャ設計では採用技術そのものの再選定ではなく、責務、保存方式、エラー処理、配布、具体的な依存バージョンを決める。

責務として、画面、作成・Clone等のユースケース、ドメイン規則、Compose生成、保存、Docker操作を分離する。UIやTauri IPCへClone Policyや競合判定を閉じ込めない。

- Desktop版の方向性: React → Tauri IPC → Core → Docker CLI Adapter。
- v2コンテナWeb版の方向性: ブラウザ上のReact → HTTP API → Rust Core → Runtime Adapter。HTTP提供とCoreを管理アプリのコンテナで実行する。

Web-readyは、CoreがTauriや画面・通信方式へ依存しないことを意味する。MVPでHTTPサーバーや認証基盤まで作ることは意味しない。v2では保存先がDockerホスト側になるため、同じCoreを使えてもパス、ポート確認、秘密管理をそのまま転用できるとは想定しない。

Docker Engine APIやPodmanへの切替え可能性はAdapter境界で残す。現時点で複数Adapterを実装したり、意味の異なる操作を過度に一般化したりしない。

## 20. プロジェクト成功条件

### リリース判断に必要な条件

| 領域 | 受入シナリオ |
| --- | --- |
| 初心者の作成 | Docker準備済みの利用者が、Compose編集やターミナル操作をせずPostgreSQLを作り、提示された情報で接続できる |
| 複数Template | PostgreSQLとRedisで、作成・管理・設定Cloneが成立する |
| Cloneの分離 | 元DBにデータを入れてCloneしても先にコピーされず、先への書込みが元へ影響しない |
| 停止中予約 | 5432を予約した停止Instanceがあるとき、Cloneが別ポートを提示し、両方同時に起動できる |
| 競合・失敗 | プレビュー後に外部プロセスがポートを使用した場合、元環境を保護したまま新候補で再試行できる |
| 永続化 | Stop／Start、コンテナ再作成後も、そのInstanceのデータが維持される |
| 中断復旧 | 作成中にアプリが終了しても、再起動後に状況を確認でき、再試行で別環境を重複作成しない |
| 標準Compose | Composeファイルがディスクに存在し、アプリ内部で構成検証・起動できる。ユーザーによる直接CLI起動は受入対象外 |
| 保存方式 | bind mountが既定であり、named volumeも設定で選択できる。両方で永続化・Clone分離・削除後の保持を確認する |
| 日本語 | 主要画面、検証メッセージ、エラー案内が日本語。生ログ・製品名・技術識別子は除く |
| 非破壊操作 | Deleteで管理外資源と永続データを削除しない。外部編集したComposeを黙って上書きしない |
| Template拡張 | 対応Schema内の追加Templateを、UI／Coreの本体コード変更なしに読み込み、作成・Cloneできる |
| 3OS対応 | Windows x86_64の64bit OS／macOS ARM64／Ubuntu 26.04の検証環境で、インストールから作成・Clone・停止まで確認する |

### ユーザー検証の暫定目標

Docker初心者5〜8名でタスク観察を行い、80%以上が支援なしで初回作成とCloneを完了することを目標案とする。所要時間は、Docker準備済み・イメージ取得時間を除いた条件で、初回作成5分以内、Clone2分以内を暫定値とする。

あわせて「複製先に元データはない」「接続ポートが変わった」「Delete後もデータは残る」をユーザーが説明できるかを確認する。目標値は実測後に見直すが、元データの共有・破壊は時間短縮のために許容しない。少人数テストの達成率を市場全体の成功率とはみなさない。

OSSとしては、Template作成ガイドと検証手順を使って、作者以外が少なくとも1つの追加定義を完成できることを成功条件とする。

## 22. この企画書から次に作るべき成果物

推奨順序は、**要件定義 → ドメインモデル → Clone Policy仕様 → Template Schema仕様 → アーキテクチャ設計 → UI／画面設計 → MVPタスク分割**とする。順番は主な確定順であり、前段の知見を受けて更新する。

| 順番 | 成果物 | 主に決めること | この順番にする理由 |
| --- | --- | --- | --- |
| 1 | 要件定義 | 利用者、対象環境、MVP境界、UC、非機能要件、受入基準、Edit／Delete／秘密管理の方針 | 技術の都合で範囲が拡大しないよう、利用者に約束する結果を先に固定する |
| 2 | ドメインモデル | Template、Instance、Project、設定、予約、データ領域、処理状態の関係と不変条件 | コンテナとInstanceを混同せず、Cloneが何を作り何を共有しないかを定める |
| 3 | Clone Policy仕様 | 項目別規則、生成・予約、確認、競合、取消し、失敗・再試行 | 最重要価値の安全条件を先に確定し、Schemaが危険な定義を許さないようにする |
| 4 | Template Schema仕様 | 入力型、Composeへの対応、Validation、Version互換、Policy宣言、信頼境界 | ドメインとCloneの意味を宣言形式へ落とす。PostgreSQL／Redisで過不足を確かめる |
| 5 | アーキテクチャ設計 | UI／Core／Adapter境界、保存と生成物、内部CLI実行、平文保存、中断復旧、3OS配布 | 確定した採用技術と振る舞いに対して実現方法を決め、v2で再利用する境界を定める |
| 6 | UI／画面設計 | 初回案内、一覧、作成、Clone差分、進捗、失敗、削除確認、接続情報 | 操作可能範囲と状態が定まったうえで、一貫した初心者向け画面へ具体化する |
| 7 | MVPタスク分割 | 依存関係、実装順、受入基準、検証・文書・配布作業 | 各タスクを要件と結び付け、作成・Cloneの利用体験単位で完了判断できるようにする |

初心者向けUXの検証は最後まで待たない。要件定義時に作成とClone確認の簡易ワイヤーフレームを用いて認識を確かめ、Clone PolicyとTemplate Schemaは往復して調整する。また、保存領域、秘密管理、CLI互換性、3OS配布の短い技術検証をアーキテクチャ確定前に行う。

MVPタスク分割では、最初に3OSでの起動・Docker診断を通し、次にPostgreSQLの作成から接続まで、続いて安全なCloneと復旧、RedisによるTemplate汎用性確認、管理操作、初心者テストと配布検証の順に、利用可能な縦の流れを積み上げる。
