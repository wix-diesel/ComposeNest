作成日: 2026-09-21\
状態: 初版ドラフト。ユーザー指定の確定方針を反映し、未指定の振る舞いを要件案として具体化\
上位文書: [企画書](product-proposal.md)

後続成果物: [v1 ドメインモデル](domain-model.md)。名前、状態、予約、削除後の保持、再試行は同文書で具体化している。

Cloneの詳細: [v1 Clone Policy仕様](clone-policy-spec.md)。型・用途別適用可否、組込み生成器、確認・確定・再試行と検証シナリオを定義している。

Templateの詳細: [v1 Template Schema仕様](template-schema-spec.md)。マニフェスト＋Version別完全定義、入力参照、パッケージ全体の読込み検証と将来のユーザー作成Templateインポートを定義している。

## 1. 目的と文書の範囲

Docker初心者が、GUIからローカル開発用サービスを作成し、既存環境を別用途へ安全に複製できるようにする。本書はv1が満たす振る舞い、制約、データ保護、受入条件を定義する。クラス、DBテーブル、IPC／HTTPの詳細、Template Schemaの構文、実装コードは後続設計へ委ねる。

本書の「必須」はv1の受入対象を意味する。ただし、ユーザー指定以外の具体化は要件案であり、合意済みの事実と混同しない。「暫定」は検証後の調整が必要な提案、「未決」は該当設計またはリリース前に解消すべき事項を示す。

## 2. 確定方針とバージョン境界

| ID | 確定方針 | 適用 |
| --- | --- | --- |
| DEC-01 | Windowsはx86_64の64bit OSのみ、macOSはARM64のみ、LinuxはUbuntu 26.04のx86_64（64bit）のみを対象とする | Windows ARM・32bit、macOS Intel、Ubuntu ARM64・32bit、他Linux・Ubuntuの他版は対象外 |
| DEC-02 | bind mountを既定とし、ユーザー設定によりnamed volumeを選択可能 | 両方式ともv1必須 |
| DEC-03 | 秘密情報は平文保存 | v1。暗号化・OS資格情報ストアは対象外 |
| DEC-04 | ユーザーによる直接CLI起動は現時点で検討しない | v1の案内・動作保証・受入から除外。アプリ内部のCLI実行は対象 |
| DEC-05 | React／Tauri／Rust／SQLiteを採用 | v1の技術制約 |
| DEC-06 | UIは日本語のみ。将来は英語等も追加 | v1では文言分離まで行う |
| DEC-07 | 管理アプリをコンテナとして起動し、ブラウザで利用可能にする | v2。v1では共通Coreの分離を行う |
| DEC-08 | Docker／Composeは現時点の最新安定版を利用する | 2026-09-21の確認基準はEngine／CLI 29.8.1、Compose 5.5.1。検証対象版を記録する |
| DEC-09 | 管理ルートをOSのシステム共通データ領域に置く | Windowsは`C:\ProgramData\ComposeNest`。各OSの採用済みパスは3.3節 |

v1はデスクトップアプリからローカルDockerを管理する。v2は管理アプリ自体のコンテナ配布とHTTP経由のブラウザ利用を追加する。v2にデータClone、多人数利用、リモート管理、英語対応まで自動的に含まれるわけではない。

## 3. 利用者・前提・対象環境

### 3.1 利用者と前提

- 主な利用者は、DBやキャッシュを利用したいDocker初心者と、複数用途の環境を分けたい開発者。
- v1は1台の端末を使う単一ユーザーと、1つのローカルDocker接続先を対象とする。
- Docker CLI、Compose、Engineは別途導入済みであることを実行前提とし、未準備の場合は日本語で案内する。
- 管理対象はLinuxコンテナ。Windowsコンテナ、本番運用、クラスタ、複数ユーザー管理は対象外。
- v1の管理アプリはDockerが停止していても起動・保存情報の閲覧ができる。コンテナを操作する処理のみDockerを必要とする。

### 3.2 対応マトリクス

| OS | 配布CPU | v1の範囲 | 未決事項 |
| --- | --- | --- | --- |
| Windows | x86_64 | 64bit OSのみ。ARM版・32bit版は対象外 | OS最低版・Docker提供形態 |
| macOS | ARM64（Apple Silicon） | macOS 15以上。Intel版・Universal版は必須にしない | Docker Desktopを含む最低版実機受入 |
| Linux | x86_64（64bit）のみ | Ubuntu 26.04のみ。他ディストリビューション・他版・ARM64は対象外。debで配布 | 配布・実機検証 |

Windowsは従来のx86系限定と64bit OS限定を合わせ、x86_64として確定する。Ubuntuはユーザー指定の26.04・64bitに加え、推奨方針の採用によりx86_64のみとする。Windows最低版は引き続き未決。macOS最低版はIssue #6で15とし、Docker Desktopの現行版が現行macOSと直前2世代をサポートする方針を基準とする。対応するDocker実行基盤とアプリの配布CPUの組合せは別途検証し、方針の確定を検証完了とみなさない。

Docker／Composeは現在の最新安定版を基準とする。2026-09-21に公式情報で確認した版は、Docker Engine／CLI 29.8.1とCompose 5.5.1である。[Docker公式リリースノート](https://docs.docker.com/engine/release-notes/29/)、[Compose公式リリース](https://github.com/docker/compose/releases/tag/v5.5.1)

この指定はコンテナイメージを`latest`タグにする意味ではない。開発・受入で使った具体的な版を記録し、以後の更新では検証基準を明示的に更新する。アプリがDockerを自動更新する機能は追加しない。Windows／macOSで使うDocker Desktop本体の版と同梱Engine／CLI／Composeの組合せは配布検証で記録する。

### 3.3 管理ルート

管理ルートは以下のシステム共通領域に確定する。2026-09-21の推奨方針採用により、管理するOSユーザーを1人に限定し、導入・初回設定時だけ必要な昇格を行う。

| OS | 管理ルート | 状態 |
| --- | --- | --- |
| Windows | `C:\ProgramData\ComposeNest` | ユーザー指定。実装時はOSのProgramData既知フォルダーから解決し、Cドライブを文字列固定しない |
| Linux（Ubuntu 26.04） | `/var/lib/composenest` | 採用済み |
| macOS | `/Library/Application Support/ComposeNest` | 採用済み |

SQLite、Template、生成Compose、bind mountデータを管理ルート配下で用途別に分離する。named volumeのデータ実体はDockerが管理し、このルート配下へ移さない。管理ルートにはvolumeの識別情報を保存する。

システム共通の保存場所を使っても、v1の複数OSユーザーによる共同管理は追加しない。初期導入時のディレクトリ作成、利用者への書込み権限付与、コンテナ内UID/GIDとの整合を設計する。平文秘密を全ユーザーへ公開せず、GUI全体の常時管理者実行を前提にしない。権限不足時は案内し、別の保存先へ黙って切り替えない。

ドメインでは管理ルートを論理的な保存基点として扱い、具体パス、所有者、ACL、インストーラーの権限処理はアーキテクチャ・配布設計で決める。

React／Tauri／Rust／SQLiteの採用は変更しない。TypeScript／Viteは企画段階の構成案を継続し、具体的なバージョンと各OSの依存物はアーキテクチャ設計で固定する。TauriのOS別前提は配布検証で確認する。[Tauri公式の前提条件](https://v2.tauri.app/start/prerequisites/)

## 4. スコープ

| v1必須 | v1対象外 |
| --- | --- |
| Docker準備診断、日本語UI | Docker自動インストール、権限の自動変更 |
| PostgreSQL／RedisのTemplate、定義追加によるフォーム生成 | 任意コードのTemplate拡張、オンラインマーケットプレイス |
| Instance作成、標準Composeのファイル生成、内部CLIによる起動 | 任意Composeインポート、直接CLI起動の支援 |
| 設定のみClone、予約ポートと保存領域の分離 | データClone、Backup／Restore |
| bind mount／named volumeの選択と永続化 | 既存データの保存方式移行、任意の既存volumeの取込み |
| 起動、停止、再起動、表示名・ポート編集、削除、ログ | DBバージョン更新、稼働DBのPassword・DB名の変更 |
| 接続情報、平文保存、UIのマスキング | 保存暗号化、OS資格情報ストア |
| 異常終了後の照合、失敗時の再試行 | 本番運用保証、外部変更との双方向同期 |
| v2へ向けたUI／Core／Adapter分離 | HTTPサーバー、コンテナ配布、認証基盤のv1実装 |

## 5. 基本概念と業務ルール

| ID | 必須ルール |
| --- | --- |
| BR-01 | Templateはサービスの宣言定義、Instanceは用途別環境、Composeは生成物として分離する |
| BR-02 | v1は1 Instance = 1 Compose Project = 1主要サービス。複数ポート・永続化対象はTemplateで表現できる |
| BR-03 | Instanceには表示名から独立した内部IDを持たせる。名称変更・再起動・コンテナ再作成でIDと保存先を変更しない |
| BR-04 | アプリ管理のInstance設定を生成の正本とする。実行状態はDockerの観測結果に基づく。UIキャッシュだけで成功と判定しない |
| BR-05 | Project名と書込み可能な保存領域をInstance間で共有しない。Templateの設定でこの条件を緩められない |
| BR-06 | ポート予約は停止・アプリ終了後も維持する。予約はOSの占有ではなくアプリ内の割当て情報である |
| BR-07 | Cloneは新しいInstanceを作る操作であり、元の設定・コンテナ・保存領域を変更しない |
| BR-08 | 既存Instanceの保存方式・保存領域・DB初期化情報の変更はv1のEditで許可しない |
| BR-09 | ユーザーによる削除操作でも永続データは残す。管理外資源と既存データを自動削除・上書きしない |
| BR-10 | v1のInstance設定、生成ファイル、予約情報は再起動後にも保持する。Template更新を既存Instanceへ自動適用しない |

表示名は日本語を許可し、前後のUnicode空白を除去してNFC正規化する。1〜100 Unicodeスカラー値とし、改行・制御文字を拒否する。有効な管理Instance間で正規化後の完全一致名を拒否する。大小文字・全半角の一律変換は行わない。これはドメインモデルで具体化した設計判断とする。内部名は表示名から分離し、Composeの制約を満たす形式へ別途生成する。

## 6. 機能要件

### 6.1 初回起動・実行前診断（UC1）

| ID | 必須要件 | 受入条件 |
| --- | --- | --- |
| ENV-01 | Docker CLI、Compose、Engine接続を個別に診断する | 不足している要素と再確認操作を日本語で表示できる |
| ENV-02 | 対応版、接続先、Linuxコンテナ実行可否を確認する | 対応外の状態でInstance作成・起動を行わない |
| ENV-03 | 実行対象を固定して操作する | 外部のContext変更で別Engineへ誤って操作しない。照合不能なら変更操作を止める |
| ENV-04 | Docker停止時にも保存済み情報を閲覧できる | Engineに接続できないとき「停止中」と断定せず「確認不能」と表示する |
| ENV-05 | 管理アプリ終了を全Instance停止として扱わない | アプリ終了だけでは起動済みコンテナを停止しない。初回にこの関係を説明する |

基本フロー: アプリ起動 → 前提診断 → 利用可能なら一覧／初回作成 → 未準備なら原因と導入・起動案内 → 再確認。

### 6.2 Template管理（UC5）

| ID | 必須要件 | 受入条件 |
| --- | --- | --- |
| TPL-01 | PostgreSQLとRedisを同梱する | 両Templateから作成・接続・永続化・設定Cloneができる |
| TPL-02 | 宣言定義からフォームを生成する | サービス固有のフォーム実装を追加せず、対応済み入力型で表示できる |
| TPL-03 | ローカル定義パッケージを読み込める | template.yamlとversions/*.yamlの追加を再起動または再読込みで反映。本体再ビルドは不要 |
| TPL-04 | ID、版、互換性、入力、Validation、保存先、Clone規則を検証する | 1 Versionでも不正・欠損ならそのパッケージ全体を拒否し、ファイルとVersionを含む理由を示す。他Template・既存登録版・Instanceは維持する |
| TPL-05 | 検証済みのサービスVersionのみ提示する | 未対応Versionを選べず、`latest`を既定値にしない |
| TPL-06 | 使用した定義と版をInstanceごとに保持する | 全Versionの完全定義と原文集合をSnapshotへ保持し、更新・削除後も別定義へ置換・新Version追加をしない |
| TPL-07 | 対応する入力型と実行能力を限定する | 文字列・整数・真偽値・選択肢・秘密文字列を扱い、任意ホストコードを実行しない |
| TPL-08 | bind mountとnamed volumeの両方を表現する | 同梱2種類のTemplateで両方式を利用できる。永続化対象を暗黙の共有領域へ逃がさない |
| TPL-09 | 日本語の項目名・説明・エラーを提供する | 日本語UIとして利用でき、内部キーと表示文字列を区別する |
| TPL-10 | ユーザー作成定義も同梱定義と同じ構文・検証へ通す | 出所はアプリ側で保持し、作者名やIDによって同梱・検証済みと偽装できない |
| TPL-11 | Templateの読込み・登録とコンテナの実行を分ける | ローカル追加の検証・登録だけではImage取得、起動、データ領域作成を行わない |

Versionごとのマウント先や初期化方法の差はTemplateが吸収する。Template本体の版、Schema版、コンテナイメージのVersionを別の概念として扱う。未知のSchema版は拒否し、同一ID・同一版の重複を読み込み順で暗黙解決しない。

Template Schema 1の標準は、共通メタ情報・Version一覧のtemplate.yamlと、Version別の完全定義ファイルで構成するパッケージとする。継承・差分マージは行わない。未実装の従来案に対する互換読込み・移行機能は設けない。登録・版管理はパッケージ全体で行う。作者はホスト側パスやClone時の資源生成を記述しない。将来のディレクトリ選択によるインポート画面でも、内容・出所の確認後に検証した同一原文集合を登録する。インポートUI、ZIP・URL取得、オンラインカタログはv1必須に追加しない。

### 6.3 保存設定（UC2・UC3）

| ID | 必須要件 | 受入条件 |
| --- | --- | --- |
| STO-01 | 初期設定はbind mountとする | 初回インストール直後の新規作成でbind mountが選択される |
| STO-02 | アプリ設定で新規作成の既定方式を変更できる | named volumeへ変更すると以降の新規フォームへ反映する。既存Instanceは変わらない |
| STO-03 | 作成・Clone確認画面で方式を選べる | bind mount／named volumeを明示して作成できる。Cloneは元の方式を初期値とする |
| STO-04 | bind mountは管理ルート配下へ新規領域を割り当てる | 内部IDに基づく領域を生成し、表示名の変更でパスが変わらない。ユーザーへ場所を表示する |
| STO-05 | bind mountの実体・権限・重複を確認する | 既存データ、管理対象領域との同一／親子重複、別表記・リンクによる重複を拒否または安全に判定できないとして停止する |
| STO-06 | named volumeはDocker上で一意な新規領域を割り当てる | 新規作成時に既存volumeを引き継がず、実名と所有対象を記録する。ホストパス入力は不要 |
| STO-07 | 再起動・再作成時はそのInstanceの保存領域を再利用する | Stop／Start、ポート変更の再作成後もデータが保たれる。新規Cloneとは扱いを分ける |
| STO-08 | 作成後の保存方式変更・データ移行は提供しない | 設定の既定値変更でデータを移動しない。Clone先で方式を変更しても元データはコピーしない |
| STO-09 | 失敗時に保存方式を自動変更しない | bind mount失敗時は原因を示し、必要なら新規環境でnamed volumeを選ぶ導線を示す |
| STO-10 | 既存Instanceの保存領域消失を空の新規環境で隠さない | 外部削除等を検出した場合は「データ保存領域が見つからない」と表示し、自動で空領域を作って起動しない |

保存ルートは3.3節のシステム共通データ領域とする。任意の既存データパス・volumeの指定、外部volume driver、ネットワーク共有領域を対象外とする。v1のユーザー設定は保存方式を対象とし、管理ルートの任意変更は必須にしない。

ドメインモデルの具体化に従い、1 Instanceの全ての書込み可能な永続化対象は同じ保存方式を使い、対象ごとに独立した領域を割り当てる。混在方式のUIはv1に追加しない。生成した設定ファイルの読取り専用マウントはデータ保存方式の選択とは区別する。

named volumeはDockerが管理する領域であり、コンテナ削除とデータ削除は別である。UIでは「Docker管理」と識別名を示し、通常のホストフォルダーとして開けるとは約束しない。[Docker volume公式資料](https://docs.docker.com/engine/storage/volumes/)

### 6.4 Instance作成・Compose生成（UC2）

| ID | 必須要件 | 受入条件 |
| --- | --- | --- |
| CRT-01 | Template選択から設定フォームへ進める | 用途名と必要最小限の入力だけで作成準備ができる |
| CRT-02 | 作成前に入力と資源を検証する | 必須・型・範囲・対応Version・ポート・保存先の問題を該当項目に表示する |
| CRT-03 | Instance設定と予約を確定し、通常のComposeを生成する | SQLiteだけに閉じ込めず`compose.yaml`がディスクに存在する |
| CRT-04 | 内部CLIで構成検証を行ってから起動する | 検証失敗時は`up`を実行しない。失敗した入力と原因を保持する |
| CRT-05 | イメージ取得、起動、準備完了確認の進捗を示す | 処理完了前に「利用可能」と表示しない |
| CRT-06 | 成功時に接続情報を示す | ホスト、ポート、必要なDB名・Username・Passwordの確認／コピーができる |
| CRT-07 | 失敗後の再試行で同じInstanceを継続する | 二重登録・別volumeの連続作成を防ぎ、既に初期化された秘密や保存先を無断で再生成しない |
| CRT-08 | Composeの手編集を検出したら変更を保留する | 外部編集を黙って上書きしない。取込みやCLI運用支援は提供しない |

基本フロー: Template選択 → 設定確認 → 入力検証 → ポート・保存領域検証 → Instanceと予約確定 → ファイル生成 → Compose検証 → 起動 → Ready確認 → 接続情報表示。

フォーム編集の段階では永続データを作成しない。作成確定後に失敗した場合は、Instanceを失敗状態として残して再試行またはデータを残す削除を選べるようにする。成功前に生成したファイル・データを無断で一括削除しない。

### 6.5 安全な設定Clone（UC3）

| ID | 必須要件 | 受入条件 |
| --- | --- | --- |
| CLN-01 | 起動中・停止中のInstanceから設定だけ複製できる | 元の稼働を中断せず、新しいInstanceを作成できる |
| CLN-02 | 元の確定値とTemplateスナップショットを使用する | CloneのためにTemplate最新版やイメージVersionへ勝手に更新しない |
| CLN-03 | 新しいID、Project、保存領域を割り当てる | 元・先が同時に稼働し、双方の永続データが独立する |
| CLN-04 | Clone Policyを適用する | 下表に従い、引継ぎ・再生成・候補探索・未設定・要入力を区別する |
| CLN-05 | 停止中と作成処理中を含む予約を考慮する | 予約済みポートを候補として確定しない |
| CLN-06 | 変更内容の確認画面を表示する | 「引継ぎ」「自動変更」「入力が必要」と「データは複製しない」を表示してから作成する |
| CLN-07 | プレビュー後に再検証する | 別処理による割当てや外部占有が発生したら再提案し、接続先を黙って変更しない |
| CLN-08 | 元環境への変更を行わない | 成功、失敗、キャンセルのどの経路でも元の設定・ファイル・データ・状態を操作しない |
| CLN-09 | 方式をまたぐ設定Cloneを許可する | bind mount→named volumeおよび逆方向で新規領域が作られ、元データは存在しない |
| CLN-10 | 初期化済みの失敗Cloneの再試行では生成値を保持する | Passwordや保存領域を再生成して初期化済みDBと不一致にしない |

| Policy | v1の意味 | 代表的な適用 |
| --- | --- | --- |
| `copy` | 元の値を保持 | Image、Version、Username、DB名、内部サービス名、保存方式 |
| `regenerate` | 型に応じた新しい値を生成 | ID、Project、保存領域、既定のPassword |
| `nextAvailable` | 利用可能な次の候補を提示 | Host Port |
| `clear` | 未設定にする | 任意項目。必須項目の場合は入力を要求 |
| `ask` | 入力・選択を明示的に要求 | 用途名、秘密情報の引継ぎ等 |

Passwordは既定で再生成し、元の値を引き継ぐ場合は明示的な選択を必要とする。秘密の差分は値を露出させず「新しく生成」「引継ぎ」と表示する。DB名やUsernameは別環境で同じでも競合と扱わない。

固定の`container_name`は使わず、Projectによる分離を使う。サービス名やcontainer側ポートは原則保持する。Clone先のネットワークは別Projectの範囲に分離する。

基本フロー: 元環境を選択 → 複製 → 新用途名 → Policy適用 → 差分・保存方式の確認 → 作成確定 → UC2の検証・起動 → 新接続先表示。

作成前のキャンセルでは候補を破棄する。作成開始後の強制キャンセルはv1必須にせず、進行状況と失敗後の再試行を提供する。元環境が外部変更されていても、未確認の実体から値を推測してCloneせず、保存済み設定を使えるか照合する。

### 6.6 ポート割当て

| ID | 必須要件 | 受入条件 |
| --- | --- | --- |
| PRT-01 | v1の公開先を127.0.0.1／TCPに限定する | 同梱Templateが外部インターフェースへ暗黙に公開しない |
| PRT-02 | 管理予約、Docker割当て、ホストの他プロセスを確認する | アプリ管理外プロセスも含め、使用が分かっているポートを提案しない |
| PRT-03 | Instance内の複数ポートもまとめて検証する | 1つでも割当て不能なら部分確定で作成成功としない |
| PRT-04 | 候補の提示と予約確定を分ける | 同時に同じ候補を見ていても、確定時に二重予約しない |
| PRT-05 | 起動直前の競合を復旧可能にする | エラー後に別候補を提示し、確認後に設定を更新して再試行できる |
| PRT-06 | 予約の存続と解放を一貫させる | 停止・失敗では保持、作成前取消しと削除完了では解放する |

要件案では入力可能範囲を1024〜65535とし、Template推奨値を起点に探索する。自動探索で範囲末尾へ到達したら先頭へ黙って巻き戻さず、別ポートの入力を促す。OS予約や確認不能な候補を「使用可能」と断言しない。外部プロセスとの競争は完全には防げないため、起動時のエラー確認を必須とする。

IPv6公開、UDP、LAN公開はv1対象外。ホストの全アドレスへの既存bindやIPv6のデュアルスタック待受がIPv4ポートへ影響する場合も、実際に利用できない候補を検出する検証に含める。

### 6.7 管理操作（UC4）

| ID | 操作 | 必須の振る舞い |
| --- | --- | --- |
| MGT-01 | 一覧・詳細 | 種類、用途名、状態、接続ポート、保存方式を表示する。詳細に保存領域、Template版、接続情報を表示 |
| MGT-02 | 起動 | 停止済みコンテナを起動し、コンテナがない場合は保持した設定から再作成。ただし保存領域消失時は止める |
| MGT-03 | 停止 | データ・設定・予約を保持してサービスを停止する |
| MGT-04 | 再起動 | 現行構成を再起動する。コンテナがない場合は起動操作を案内し、設定変更の適用操作として扱わない |
| MGT-05 | 編集 | 表示名は未解決の変更操作がなければ変更可能。接続ポートは停止またはコンテナ不在を確認した状態で変更可能。確認不能は不可。DB初期化値・Version・保存方式は変更不可 |
| MGT-06 | ポート変更の適用 | 新ポートを検証・予約し、Compose再生成と必要な再作成を行う。操作後も停止状態を維持し、データを保持 |
| MGT-07 | 削除 | 対象と影響を確認して実行資源を除去し、有効な一覧から外す。bindデータとnamed volume、復旧用情報を残す |
| MGT-08 | ログ | 対象Instanceのログを上限付きで表示し、再読込みと追従停止ができる |
| MGT-09 | Compose確認 | 生成物を閲覧し、保存フォルダーの場所を確認できる。秘密を含む表示は明示操作にする |
| MGT-10 | 二重操作防止 | 同じInstanceの変更操作を直列化し、ボタン連打・複数ウィンドウで競合しない |

ポート編集の途中で失敗した場合は旧値と新値を区別し、再試行または元設定への復帰が完了するまで必要な予約を保持する。保存成功と実行構成への反映成功を混同しない。

ドメインモデルでは旧確定設定と変更予定を分け、旧Committed予約と新Held予約を保持し、実体反映と停止を確認してから確定・解放する。確認用の作成・Clone計画は永続予約を取得せず、作成確定時に再検証する。

削除画面は「環境を削除。データは残ります」と表示し、bind mountならパス、named volumeなら識別名を示す。削除記録には残存領域を識別できる情報を残し、新規作成で再利用しない。削除失敗時は有効な登録と予約を保持して再試行する。volume削除を伴う一括操作は実行しない。

有効登録の削除は、ドメインモデル上のRetired化とする。Instanceの最小記録と領域の所有関係を保持し、物理レコード消去を要求しない。未完了の削除はRetiringとして保持し、復活やデータ完全削除の機能は追加しない。

## 7. 状態・失敗・復旧要件

単一の状態文字列で全てを表現せず、「実行状態」「処理の進捗／結果」「構成の一致状況」を分けて管理することを要件とする。内部の状態機械はドメインモデルで定義する。

| 観点 | UIで識別する状態例 |
| --- | --- |
| 実行状態 | 未作成、停止中、実行中・準備中、利用可能、異常、確認不能 |
| 処理 | 作成中、イメージ取得中、起動中、停止中、編集適用中、削除中、完了、失敗 |
| 構成 | 一致、外部変更あり、生成物不足、保存領域不足 |

| ID | 必須要件 |
| --- | --- |
| REC-01 | Dockerに接続できない場合は直近の観測時刻を示し、停止や削除済みと推測しない |
| REC-02 | コンテナが実行中でもHealth Checkが成功するまで利用可能としない。同梱Templateは準備完了の検査を持つ |
| REC-03 | 処理段階と生成済み資源を記録し、アプリ異常終了後にSQLite・ファイル・Dockerを照合する |
| REC-04 | 起動タイムアウト時もコンテナが動いている可能性を表示し、実態を再確認してから再試行する |
| REC-05 | 未完了処理の再試行は同じID・保存領域・秘密情報を継続し、二重作成を防ぐ |
| REC-06 | 一部資源ができた状態で失敗しても、元環境や他環境のデータを削除しない |
| REC-07 | Docker停止、容量不足、取得失敗、ポート競合、保存権限、Template不正、外部変更を区別して日本語で案内する |
| REC-08 | 不整合の理由を判断できない場合は変更処理を保留する。データを消す自動修復を行わない |

ログやComposeの閲覧可能性と操作可否は分ける。外部で構成を書き換えられた場合は任意のCompose内容をそのまま実行しない。実行対象の照合と、確認後に変更ファイルを退避して保存設定から復帰する方法は、[アーキテクチャ設計](architecture-v1.md)の6.3節・8.2節で具体化している。

## 8. 保持する情報

以下は論理的な情報要件であり、テーブル定義ではない。

| 情報 | 必須内容・保持条件 |
| --- | --- |
| アプリ設定 | 新規作成の既定保存方式、管理ルート、対象Docker接続先、日本語表示の設定基盤 |
| Template | ID、定義版、Schema版、入力・検証・実行・Clone定義、対応条件 |
| Instance | 内部ID、表示名、元Templateとスナップショット、確定値、Project名、作成日時、Clone元ID（由来としてのみ） |
| 保存領域 | 方式、bind実体パスまたはvolume実名、所有Instance、作成・初期化状況 |
| ポート予約 | 対象Engine、IP、プロトコル、ポート、所有Instance、確定／処理中の区別 |
| 生成物 | Composeと必要な補助ファイル、生成版、改変検出に必要な情報 |
| 操作と状態 | 処理ID、処理段階、最終結果、最後の観測時刻、再試行に必要な情報 |
| 削除後の情報 | 残したデータ領域、元の設定・生成物の所在、削除結果。有効なポート予約は保持しない |

Instanceと予約の構造化した永続状態にはSQLiteを使う。秘密情報を含め平文保存を許容するが、正本と生成物の関係を明記し、ログや一時ファイルに不要な複製を作らない。Clone元の削除によってClone先を削除する参照関係にしない。

## 9. 秘密情報・権限・入力保護

| ID | 必須要件 | 受入条件 |
| --- | --- | --- |
| SEC-01 | v1の保存は平文とし、その事実を説明する | 設定と初回の認証情報入力時に「暗号化せず保存」と表示する。暗号化済みと誤認させない |
| SEC-02 | 通常画面では秘密情報を隠す | 表示／コピーは明示操作。Clone差分や一覧に生の秘密を表示しない |
| SEC-03 | 管理データは指定したシステム共通領域へ保存し、利用者の権限を設定する | 全ユーザーへの読書きを許可せず、通常実行時に必要な権限で操作できる。秘密入り生成物の共有の影響を案内する |
| SEC-04 | ログへの秘密情報出力を抑える | アプリ自身は既知の秘密を記録しない。CLI診断出力を抑制・マスキングする。任意のサービスログを完全秘匿できるとは保証しない |
| SEC-05 | 秘密の文字を正しく扱う | Templateが許可した`$`、引用符、空白等がCompose展開で変質せず、接続に使う値と一致する |
| SEC-06 | ホストシェルを介した入力展開を避ける | UIやTemplateの値を任意ホストコマンドとして実行できない |
| SEC-07 | Templateの実行権限を制限する | 特権、Docker socket、host network、任意ホストパス、任意ホストコードを管理対象Templateで許可しない |
| SEC-08 | 平文保存の方針をネットワーク公開へ拡大しない | v1はlocalhost公開・単一ユーザーを維持。認証情報や構成を外部送信しない |

平文保存は暗号化実装を省く判断であり、常時表示や診断情報への露出を要求するものではない。SQLiteや生成物を読める利用者は秘密を取得できるという限界を明記する。v2で管理アプリへDocker接続権限を与える設計は、v1 Templateでのsocket禁止とは対象が異なるため別途検討する。

## 10. 非機能要件

| ID | 領域 | v1要件 |
| --- | --- | --- |
| NFR-01 | 日本語 | アプリ作成文言、フォーム、ヘルプ、検証・エラー案内は日本語。Dockerの生ログ、製品名、技術識別子は翻訳対象外 |
| NFR-02 | 多言語化準備 | 文言を安定したキーで分離し、エラーは識別子と表示文言を分ける。将来の翻訳にDBの識別値変更を必要としない |
| NFR-03 | 応答性 | CLI処理とイメージ取得で画面操作をブロックしない。実行開始または受付を1秒以内に示すことを暫定目標とする |
| NFR-04 | 状態更新 | 操作完了後に実態を再取得する。手動更新を用意し、自動取得不能時は最終観測を示す |
| NFR-05 | 制限 | ログ表示・取得待ち・再試行を無制限にしない。採用済み初期値はログ2,000行または2 MiBの小さい方、準備完了待ち180秒、別枠のイメージ取得待ち15分。対象OS・Templateの実測で調整し、タイムアウト後は実体を再確認する |
| NFR-06 | 信頼性 | 異常終了後の照合、同一Instanceの排他、処理単位の再試行を備える。DBとDockerが同一トランザクションで動くとは仮定しない |
| NFR-07 | アクセシビリティ | 主要操作をキーボードで行え、ラベル・フォーカスを設け、状態を色だけで伝えない |
| NFR-08 | クロスプラットフォーム | 合意した各OS／CPUで両保存方式を検証し、日本語・空白を含むユーザーパス、権限、Engine停止を確認する |
| NFR-09 | 保守性 | Clone・検証・保存ルールをReactやTauri IPCへ埋め込まず、Rust Coreから再利用可能にする |
| NFR-10 | Adapter | Docker CLI、ファイルシステム、接続先、ホストのポート確認を境界化し、HTTPや管理コンテナからの利用を妨げない |
| NFR-11 | 配布 | Dockerコンテナ起動を要求しない通常のデスクトップパッケージを各対象OSへ用意し、前提依存と導入手順を示す |
| NFR-12 | OSS運営 | 公開前にライセンス、開発手順、Template作成・検証手順、脆弱性報告窓口を用意する |

性能の暫定評価条件はローカルの管理Instance 30件とし、実機の基準を検証計画で定める。ネットワーク速度に依存するイメージ取得時間を初回作成UIの性能保証へ含めない。配布形式はNSIS／署名・公証済みappと初期設定用pkg／deb、更新は署名済みパッケージによる手動更新を採用済み。署名体制・配布工程・実機検証はリリース前に完了する。詳細は[アーキテクチャ設計](architecture-v1.md)の11節・14節を参照する。

## 11. v2コンテナWeb版へ引き継ぐ制約

v2の到達点は、管理アプリをコンテナで起動し、ブラウザからTemplates／Instancesを利用できること。以下はv1で保つ境界と、v2で決める事項を分けたものとする。

| ID | v1で必要な準備 | v2で定義する事項 |
| --- | --- | --- |
| FUT-01 | Rust CoreをTauriから独立させる | HTTP API、Web配信、管理コンテナの起動・配布方式 |
| FUT-02 | UIからホストパスやDockerを直接操作しない | Dockerへの接続方法、socket等の権限、対象ホスト |
| FUT-03 | 保存先を実行ホストに紐付ける | 管理コンテナ内パスとDockerホスト上のbind sourceの対応 |
| FUT-04 | ポート検査を実行環境の境界へ置く | 管理コンテナ自身のポート空き確認ではなく、対象ホスト上での占有判定 |
| FUT-05 | SQLite・Template・生成物の保存先を明確化する | 管理コンテナ再作成後の状態永続化、デスクトップ状態の移行要否 |
| FUT-06 | 秘密管理を画面から分離する | v2の保存保護、HTTP認証、公開範囲、CSRF等のWeb固有対策 |

bind mountのsourceはDocker daemon側のパスであり、ブラウザ利用者や管理コンテナ内のパスをそのまま指定できるとは限らない。v2では「どのホストの保存領域か」を明示する必要がある。[Docker bind mount公式資料](https://docs.docker.com/engine/storage/bind-mounts/)

v1のサービス接続先はlocalhostでよいが、v2のリモートブラウザにlocalhostを提示すると利用者端末を指してしまう。管理画面のURL、サービスの接続先、Dockerホストを別の値として設計する。v2の公開ネットワーク、認証、複数ユーザー対応はこの要件定義では確定しない。

## 12. 受入シナリオと追跡

以下をv1の受入計画へ引き継ぐ。各項目のテスト実装は後続タスク分割で決める。

| ID | シナリオ | 合格条件 | 主な要件 |
| --- | --- | --- | --- |
| AC-01 | Docker未導入・Compose不足・Engine停止で起動 | 原因が日本語で分かり、保存情報を失わず再確認できる | ENV-01〜04 |
| AC-02 | 初期設定でPostgreSQL作成 | bind mountで起動し、提示された情報で接続できる | STO-01、CRT-01〜06 |
| AC-03 | 設定をnamed volumeへ変更してRedis作成 | 新規フォームへ反映し、Redisがnamed volumeを使用。既存DBは変わらない | STO-02、TPL-01 |
| AC-04 | 各Templateを両方式で作成し停止・起動・再作成 | 作成後のテストデータが保たれる。RedisはTemplateで永続化を有効にしたうえで確認 | TPL-08、STO-07、MGT-02〜06 |
| AC-05 | 元にデータを作り同方式へClone | 新しい保存領域で元業務データがなく、先への書込みが元に影響しない | CLN-01〜06、BR-05 |
| AC-06 | bind→namedとnamed→bindのClone | 方式は指定どおり、保存領域は新規、データ移行をしない | CLN-09、STO-03・08 |
| AC-07 | 停止中の5432予約がある状態でClone | 別ポートを提示し、元と先を同時起動できる | CLN-05、PRT-02〜06 |
| AC-08 | 同時作成、プレビュー後の外部占有 | 二重予約しない。起動時競合なら候補を再提示し、確認後に再試行できる | PRT-04・05、CLN-07 |
| AC-09 | Cloneのキャンセル・取得失敗・準備完了失敗 | 元環境は変わらず、再試行でID・保存先・Passwordが変わらない | CLN-08・10、CRT-07、REC-04〜06 |
| AC-10 | 別表記のパス、親子領域、既存volumeが衝突 | 既存データを共有せず拒否または新規割当てできる | STO-04〜06 |
| AC-11 | 既存Instanceの保存先を外部で削除 | 空のDBとして無断再起動せず、領域消失を案内する | STO-10 |
| AC-12 | Stop・Restart・表示名編集・ポート編集 | データ・内部IDを保持し、ポート編集完了後は停止状態。接続情報が確定値と一致 | MGT-02〜06 |
| AC-13 | 両方式のInstanceを削除 | 対象実行資源と有効登録のみ削除。データと所在情報を保持、成功後に予約解放 | MGT-07、BR-09、PRT-06 |
| AC-14 | 作成・編集・削除の途中でアプリ異常終了 | 再起動後に照合でき、二重環境作成・誤削除をしない | REC-03・05・08 |
| AC-15 | Compose手編集、外部Context切替え | 無断上書き・別Engineへの誤操作を止める | CRT-08、ENV-03 |
| AC-16 | 追加Template、不正Template、旧定義削除 | 有効な追加を本体変更なしで利用し、不正定義は分離。既存環境は保存済み定義を維持 | TPL-02〜09 |
| AC-17 | 平文保存と秘密表示 | 平文の説明があり、通常画面はマスク、表示／コピーは明示操作。許可された特殊文字で接続できる | SEC-01〜05 |
| AC-18 | 各対応OSで主要フロー | 2 Template × 2保存方式の作成・Clone・管理が成立。UIは日本語 | DEC-01、NFR-01・08・11 |
| AC-19 | 生成物と採用技術を確認 | Composeがディスクに存在し内部CLIで起動可能。React／Tauri／Rust／SQLiteの責務分離を確認 | DEC-05、CRT-03・04、NFR-09 |
| AC-20 | 初心者による作成とClone | Compose手編集なしで接続し、データ非複製・ポート変更・削除時保持を説明できる | CRT-01、CLN-06、MGT-07 |

AC-05・06・09・10・13は両Templateと両保存方式を組み合わせて検証する。全ての障害注入を各OSで重複実施するかは検証計画で決めるが、OS固有のパス・権限・ポート差は各対象環境で確認する。

初心者5〜8名の観察で80%以上が支援なしに作成・Cloneを完了することを暫定目標とする。Docker準備済み・イメージ取得時間を除き、作成5分以内、Clone2分以内を計測する。安全性条件は操作時間との交換条件にしない。

## 13. 決定事項と実装・検証の残件

2026-09-21にOPN-02のUbuntu x86_64限定と、OPN-03〜12の推奨方針をユーザーが採用した。方針の決定と、実装・実機検証の完了は区別する。当時はWindows／macOS最低版が未決だったが、macOSはIssue #6で15を下限とした。Windows最低版とmacOS 15でのDocker Desktopを含む実機受入は残る。

## 14. 次の成果物への引継ぎ

1. **ドメインモデル:** BR、STO、PRT、RECを使い、Instanceの同一性、予約、保存領域、処理状態と不変条件を定める。
2. **Clone Policy仕様:** CLNとPRTを使い、生成・候補提示・確定・失敗・再試行の意味を厳密化する。
3. **Template Schema仕様:** TPLとSECを使い、2つのサービスと両保存方式を宣言で表現する。厳密な構文はここで決める。
4. **アーキテクチャ設計:** 確定技術を前提に、SQLiteと生成物、内部CLI、OS依存、v2の再利用境界、異常終了時の整合を設計する。
5. **UI／画面設計:** 日本語の通常操作、保存方式設定、Clone差分、失敗復旧、削除時保持を具体化する。
6. **MVPタスク分割:** 本書の要件IDとACを紐付けて、3OS基盤、作成、保存、Clone、管理、検証・配布を縦の利用フローで分割する。

ドメインモデル、Clone Policy仕様、Template Schema仕様、[v1 アーキテクチャ設計](architecture-v1.md)を作成済み。アーキテクチャでは責務境界、物理テーブル構成、生成物、CLI操作と復旧を具体化した。未決事項の具体化と実機検証の残件は同書14節を参照する。[v1 実装タスク一覧](https://github.com/wix-diesel/ComposeNest/issues/56)に小さなPR単位のタスクと依存関係を整理済み。UI／画面の具体化は対応タスクで行う。アプリ実装コード・DB migrationは未実装である。
